# 링크 저장 준비는 ContentService의 링크·스크린샷 진입점이 맡는다

콘텐츠 저장은 `ContentService`의 진입점 두 개, 링크 저장(`save_link`)과 스크린샷 저장(`save_screenshot`)으로 받는다.
공유 저장은 링크 저장에 공유 정보(공유 텍스트·공유 앱 등)를 더해 넘기는 경우로 다룬다.
링크 URL 필수 검사, YouTube 판별·정규화, 메타데이터 추출 실행과 보강, 사용자 입력 판정, 이벤트 metadata 조립,
저장 시 카테고리 추천은 링크 저장 안에 둔다. 그래서 라우트·공유 저장·업로드는 이 정책을 몰라도 된다.
이 결정은 ADR 0003이 "링크 저장 준비를 한 module로 정리할 때" 다시 검토하기로 한 항목에 대한 답이다.
이 리팩터링은 `/api/v1` 요청·응답·상태 코드·오류 문구, DB 스키마, `content_created` 이벤트 metadata,
요약 작업 플래그, 로그를 바꾸지 않는 것을 전제로 한다. 2026-11-07 설계 회의에서 합의했으며, 구현 완료를 뜻하지 않는다.

사용자 입력 판정은 YouTube·그 밖의 링크 모두 "추출 전 원래 입력값"으로 통일한다. ADR 0003이 미뤄 둔 판정 통일이다.
다른 주소에서 리다이렉트되어 YouTube가 되는 링크는 메타데이터 값을 사용자 입력으로 보던 동작을
보존용 임시 분기로 남겼다가 #281에서 없앴다.

## 검토한 대안

- **진입점 세 개(링크·공유·스크린샷)**: 공유와 링크는 공유 정보만 빼면 처리가 같아 중복이나 얕은 전달 함수가 생긴다.
- **명령 객체 하나(`create_content(request: LinkSave | ScreenshotSave)`)**: 깊이는 같고 분기가 함수 이름 대신 타입 검사로 바뀔 뿐이다.
- **서비스 오류를 도메인 오류로 바꾸기**: 서버의 모든 서비스가 `app/core/exceptions.py`의 `HTTPException` 하위 클래스를 던진다.
  이 서비스만 바꾸면 방식이 둘이 되고, 예외 처리기를 operator-recovery 검사 대상인 `main.py`에 넣어야 한다.
  상태 코드와 문구를 그대로 두고 서버 전체 방침으로 따로 다룬다.
- **YouTube 공유에도 공유 정보를 이벤트 metadata에 넣기**: 진입점이 하나로 모이면 자연스럽지만 지표 데이터가 바뀐다.
  지금처럼 YouTube 공유에는 공유 정보와 공유 텍스트 추천을 넣지 않고, 지표 쿼리를 확인한 뒤 따로 바꾼다.

## 재검토 조건

리다이렉트 YouTube 버그 이슈를 처리할 때, 서비스 오류를 HTTP와 분리할 때, YouTube 공유의 이벤트 metadata를 바꿀 때
이 결정을 다시 검토한다.
