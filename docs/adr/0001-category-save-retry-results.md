# 카테고리 저장 재시도를 위해 제출별 처리 결과를 보관한다

카테고리 생성·수정은 서버에 반영된 뒤 응답만 유실될 수 있으며, 현재 목록 조회나 이름 중복 오류로는 해당 제출의 결과를 확정할 수 없다.
2026-10-25 설계 인터뷰 Q8에서 기존 서버를 유지한 안내·목록 확인만 제공하는 대안 대신, 서버가 제출별 식별자와 처리 결과를 보관하고 같은 제출의 재시도에 기존 결과를 재사용하도록 API·DB 지원을 추가하기로 합의했다.
이는 응답 유실 후 같은 시트의 제출을 복구하기 위한 선택이며, 클라이언트·서버의 계약을 늘리는 비용을 수용한다. Q10·Q11에 따라 결과 미확인 중에는 같은 제출만 다시 확인하고, 시트를 닫거나 앱을 종료한 뒤의 자동 복원·재전송은 제외한다.

Q13·Q14에 따라 이후 수정·삭제를 재시도로 되돌리지 않으며, 서버의 최소 처리 기록은 자동 만료시키지 않고 계정 탈퇴 시 함께 삭제한다. 카테고리를 삭제해도 기록은 유지한다. 서버는 계정과 제출 키별 처리 기록을 `category_submissions`에 보관하고, 생성·수정과 같은 트랜잭션에서 결과를 확정한다. 앱은 현재 시트에서 같은 키와 제출 내용으로 재확인한다. 현재 계약은 [정책](../frontend/category-save-recovery.md)과 [API 안내](../backend/api-contracts.md#카테고리-생성수정-제출-복구)를, 적용·검증 범위와 배포 여부는 [구현 이력](../history/2026-10-25-category-save-recovery-implementation.md)을 따른다.

Q17에서 재확인은 단순 조회가 아니라 원래 저장 의도를 이어가는 행동임을 명시적으로 확인했다. 처리 기록이 없다면 원래 제출의 저장을 진행할 수 있고 이미 처리 중이면 중복 실행하지 않는다. 이미 처리했다면 기록된 결과를 재사용한다.
