# 업데이트 내역과 배포 관리

[변경 이력](../CHANGELOG.md)은 사용자에게 보이는 변경 내용의 원본입니다.
배포마다 [배포 기록 양식](releases/TEMPLATE.md)을 복사해 실제 산출물·진행 상태·검증 근거를 남깁니다.
이 체계는 2026-10-22 (KST)부터 적용하며 과거 이력을 복원하지 않습니다.

## 변경 작성과 PR 리뷰

1. 작성자는 사용자에게 보이는 기능·동작 변경을 같은 PR의 `CHANGELOG.md` 안 `미배포`에 적습니다.
   커밋 메시지를 나열하지 않고 사용자가 경험하는 변화를 한국어로 설명합니다.
2. 새 기능은 `추가`, 기존 경험의 개선은 `개선`, 잘못된 동작의 교정은 `수정`으로 분류합니다.
   각 항목에 `[앱]`, `[iOS]`, `[Android]`, `[서버]`로 적용 범위를 표시합니다.
   `[앱]`은 양 모바일 플랫폼에 공통인 앱 변경에 사용합니다.
3. [PR 템플릿](../.github/pull_request_template.md)의 변경 이력 항목 중 하나만 선택합니다.
   반영한 경우 항목이나 위치를, 제외한 경우 사용자 동작에 영향이 없는 이유를 적습니다.
   문서·테스트·동작 변화 없는 정리는 제외할 수 있습니다.
   이 관리 체계의 최초 도입도 문서와 템플릿만 변경하므로 사용자 변경 이력에서 제외합니다.
4. 리뷰어는 이력 또는 제외 사유가 실제 diff와 일치하는지 확인합니다.
   일부 사용자 변경이 있는 PR은 문서·테스트도 포함한다는 이유로 전체를 제외하지 않습니다.
   이 규칙은 PR 템플릿과 리뷰로 확인하며 CI 자동 검사는 두지 않습니다.

## 배포 준비

1. 배포 담당자는 실제 포함할 변경과 소스 커밋을 확정합니다. `미배포` 전체를 자동으로 포함하지 않습니다.
2. 앱 배포는 사용자용 버전과 플랫폼별 빌드 번호를 정합니다.
   [pubspec.yaml](../frontend/pubspec.yaml)의 버전은 기본값이며, 빌드 인자로 덮어썼다면
   실제 산출물의 버전·빌드 번호를 기록합니다. 기존 스토어 업로드 번호를 확인한 뒤 새 번호를 정합니다.
   서버 단독 배포 때문에 앱 버전을 올리지 않습니다.
3. 양식을 `docs/releases/` 안에 복사합니다. 앱의 각 후보는 `app-vX.Y.Z-ios-bN-android-bM.md`로 기록합니다.
   한 플랫폼만 대상이면 다른 플랫폼 부분을 생략하고 양 플랫폼은 항상 iOS, Android 순서로 씁니다.
   `app-vX.Y.Z.md` 버전별 개요가 있으면 후보 기록과 최종 선택한 빌드를 수동으로 연결합니다.
   첫 후보는 개요 없이 만들 수 있으며, 후보가 여러 개면 개요를 만들어 연결할 수 있습니다.
   서버 단독 후보는 KST 배포 준비 날짜와 같은 날의 회차를 사용한 `backend-YYYY-MM-DD-N.md`입니다.
   서버 회차는 1부터 시작합니다. 앱과 서버를 함께 배포하면 앱 후보 기록의 서버 영역에 함께 적습니다.
4. 포함되는 항목만 `CHANGELOG.md`의 `앱 X.Y.Z` 또는 `backend-YYYY-MM-DD-N` 제목 아래로 옮기고,
   해당 배포 기록으로 링크합니다. 앱은 개요가 있으면 개요를, 없으면 후보 기록을 연결합니다.
   `미배포`와 추가·개선·수정 구분은 유지하며 미포함 항목은 남깁니다.
   준비 중인 버전에는 공개일을 미리 넣지 않습니다.
5. 플랫폼별 대상 여부·소스 SHA·버전·빌드 번호와 서버 대상 여부·SHA·마이그레이션을 기록합니다.
   소스 SHA는 빌드할 커밋에서 아래 명령으로 확인하고 실제 산출물과 대조합니다.
   배포 후 문서만 수정한 커밋의 SHA로 빌드 SHA를 바꾸지 않습니다.

   ```bash
   # 저장소 루트의 빌드 대상 커밋에서 실행
   git rev-parse HEAD
   ```

6. 앱이 새 API·DB 구조에 의존하면 필요한 서버·마이그레이션·앱 배포 순서와 기존 앱 호환성을 먼저 적습니다.
   실제 실행하지 않은 마이그레이션이나 운영 검증을 완료로 표시하지 않습니다.

## 버전 결정

앱 사용자 버전, 플랫폼별 빌드 번호, 서버 배포 식별자, API 계약 버전, DB migration revision은 서로 구분합니다.
서버의 패키지·OpenAPI 문서 버전은 기존 정의를 따르며 서버 배포 식별자와 같은 값으로 자동 변경하지 않습니다.

| 앱 변경 | 올릴 숫자 | 예시 |
| --- | --- | --- |
| 오류 수정·기존 흐름을 유지하는 작은 사용성 개선 | PATCH: `X.Y.Z`의 Z | `1.2.0` → `1.2.1` |
| 새 기능·의미 있는 기능 개선 | MINOR: Y를 올리고 Z를 0으로 초기화 | `1.2.1` → `1.3.0` |
| 주요 기능 제거·데이터 전환 등 별도 안내가 필요한 큰 변화 | MAJOR: X를 올리고 Y·Z를 0으로 초기화 | `1.3.0` → `2.0.0` |

- 여러 변경을 묶으면 가장 큰 변경 기준을 적용합니다. 커밋의 `feat`·`fix`만으로 자동 결정하지 않습니다.
- 정식 공개 전에는 `0.x.y`를 사용하며 기능 추가는 가운데 숫자, 수정은 마지막 숫자를 올립니다.
  `1.0.0`은 출시 범위의 저장·조회·검색·삭제 등 핵심 흐름과 계정·데이터 보존·복구 등 운영 준비를
  검증하고 지속적으로 지원할 첫 정식 공개 기준점입니다. 구체적인 출시 범위·검증 목록·출시일은 출시 준비에서 확정합니다.
- 같은 기능 묶음의 iOS·Android는 사용자 버전을 공유합니다. 각 플랫폼의 빌드 번호·소스·공개 상태는 별도입니다.
  새 배포용 산출물은 기존 스토어 업로드 이력을 확인한 더 높은 빌드 번호로 식별합니다.
  초기 관리 규칙은 플랫폼마다 양의 정수 빌드 번호를 사용하고, 사용자 버전을 바꾸어도 이미 사용한 번호를 재사용하지 않습니다.
- 테스트 중에는 목표 사용자 버전을 유지하고 수정할 때 새 빌드 번호를 씁니다.
  최종 검증한 빌드를 정식 배포 대상으로 지정합니다. 정식 공개 후 앱 수정은 새 사용자 버전으로 준비합니다.
- 서버만 수정하면 앱 버전은 유지하고 새 서버 배포 식별자를 사용합니다.
  앱 MAJOR 증가나 서버 배포 횟수만으로 `/api/v1` 같은 API 계약 버전을 올리지 않습니다.

## 후보 식별과 소스 고정

| 대상 | 태그 이름 | 후보 기록 파일명 |
| --- | --- | --- |
| iOS | `app-ios-vX.Y.Z-bN` | `app-vX.Y.Z-ios-bN.md` |
| Android | `app-android-vX.Y.Z-bM` | `app-vX.Y.Z-android-bM.md` |
| 양 플랫폼 | 플랫폼별 태그를 각각 사용 | `app-vX.Y.Z-ios-bN-android-bM.md` |
| 서버 단독 | `backend-YYYY-MM-DD-N` | `backend-YYYY-MM-DD-N.md` |

- 후보는 배포를 준비하는 특정 소스와 산출물 조합입니다. 태그는 해당 전체 소스 SHA를 고정하는 표시이며 실제 배포 성공을 뜻하지 않습니다.
  같은 기능 묶음이어도 플랫폼별 소스가 다르면 각 태그를 해당 소스에 연결합니다.
- 태그를 만들기 전에 로컬·원격의 같은 태그와 기존 기록을 확인합니다. 이미 존재하는 태그를 다른 커밋으로 옮기거나
  같은 플랫폼의 빌드 식별자를 새 후보에 재사용하지 않습니다. 기존 후보를 다시 실행할 때는 기록된 태그·SHA·산출물을 그대로 대조합니다.
  후보 기록에 예약한 빌드 번호도 사용 중인 것으로 취급하며, 다른 사용자 버전이나 다른 플랫폼 조합의 후보에서도 재사용하지 않습니다.
  플랫폼 간에는 빌드 번호를 독립적으로 판단합니다.
- 같은 산출물의 업로드 재시도·중단 후 재개는 기존 후보의 진행 기록에 이어 적습니다.
  앱 소스를 수정하거나 새 산출물을 만들면 새 빌드 번호·후보 기록을 사용합니다.
  서버 소스를 수정하면 새 날짜·회차 식별자를 사용합니다. 실패한 후보의 기록·태그는 보존합니다.
- 새 후보 기록으로 이전 파일을 덮어쓰지 않습니다. 같은 앱 버전의 추가 후보는 새 파일로 만들고
  버전별 개요가 있으면 링크를 추가합니다. 기존 `app-vX.Y.Z.md` 안에 작성한 상세 이력이 있으면 보존하고 새 후보부터 분리합니다.
- 스토어 업로드 이력·원격 태그 조회의 출처와 확인 시점을 남깁니다. 조회 실패나 로컬 기록만으로 전역 중복 없음,
  배포 준비 완료를 선언하지 않습니다. 확인되지 않은 항목은 이유와 함께 `미확인`으로 남깁니다.
- 자동화는 사람이 선택한 변경·소스·버전을 검사하고 초안을 만드는 데서 시작합니다. 초안 생성은 산출물 생성·SHA 일치 검증이나
  운영 반영의 증거가 아닙니다. 자동 버전 증가·태그 생성·푸시·업로드·배포를 초안 생성의 부수 효과로 실행하지 않습니다.

## 기존 앱 호환성과 지원 종료

- 서버 변경은 이미 배포한 앱과의 호환성을 기본으로 유지합니다. 새 앱 공개만으로 기존 필드나 동작을 바로 제거하지 않습니다.
- 호환되는 서버·마이그레이션을 먼저 배포하고, 새 앱을 공개한 뒤 구버전 사용 현황과 전환 조건을 확인합니다.
  구버전 지원 종료는 대상·시점·안내·전환 조건을 별도 결정으로 기록한 뒤 진행합니다.
  API 호환성을 끊는 계약 변경은 별도의 API 전환 계획으로 다룹니다.
- 보안 문제 등 긴급 예외는 사유·영향·대상 앱·전환 조치와 실제 결과를 기록합니다.
  이 원칙만으로 강제 업데이트 기능이나 사용량 수집 시스템을 추가하지 않습니다.

## 판단 예시

다음은 정책 대조용 예시이며 실제 공개·배포 이력이 아닙니다.

| 상황 | 버전·기록 판단 |
| --- | --- |
| 공개한 `1.2.0` 앱의 화면 오류 수정 | `1.2.1`과 플랫폼별 새 빌드 번호로 후보 준비 |
| `1.2.1`에 새 정리 기능 추가 | `1.3.0`, PATCH 변경을 함께 포함해도 MINOR 기준 적용 |
| `1.3.0`의 주요 기능 제거·데이터 전환 | 별도 전환 안내를 준비하고 `2.0.0` 후보로 기록 |
| 서버 이미지 처리만 수정 | 앱 버전 유지, `backend-2026-10-27-1`과 서버 SHA 기록 |
| `0.2.0` 테스트 빌드 21 수정 | 목표 `0.2.0` 유지, 빌드 22와 새 후보 파일·태그 사용 |
| iOS 먼저 공개, Android 심사 중 | 사용자 버전은 같아도 iOS만 공개일 기록, Android는 심사 중으로 유지 |
| 검증한 빌드 22의 업로드 재시도 | 동일 후보 진행 기록에 실패·재시도를 추가하고 빌드·SHA를 바꾸지 않음 |

## 검증과 스토어 등록

- 모바일 실행·설정은 [프론트 README](../frontend/README.md),
  iOS 업로드는 [TestFlight 권한 설명과 재업로드](frontend/development.md#testflight-권한-설명과-재업로드)를 따릅니다.
  Flutter 빌드의 앱 진입점은 `lib/main.dart`로 명시하고 산출물의 실제 버전·빌드 번호를 확인합니다.
- 백엔드 검사는 [백엔드 검증 안내](backend/testing.md#validation),
  운영 배포·마이그레이션·복구는 [Railway 배포·복구](railway-deployment.md)를 따릅니다.
  이 문서에 실행 명령이나 공급자 설정을 중복 복사하지 않습니다.
- 배포 기록의 검증 표에 실제 명령·시나리오·결과·근거를 남깁니다.
  로컬 자동 검사·대역 데이터, 원격 CI, iOS Simulator, Android Emulator,
  실제 OAuth·공급자, 운영 서버, 실기기 결과를 구분합니다.
  모바일 실행은 기종·OS와 화면·동작 증거도 기록합니다.
- 스토어 안내는 해당 배포의 변경 이력에서 사용자에게 필요한 내용을 추려 등록합니다.
  플랫폼에 적용되지 않거나 아직 제공되지 않는 기능은 안내에서 제외합니다.
  별도의 수기 원본 파일을 만들지 않고, 등록 후 변경 이력과 의미가 일치하는지 확인합니다.
- 문서·템플릿만 변경한 작업은 링크·경로·명령·내용과 `git diff --check`를 확인합니다.
  이 경우 앱 테스트·빌드·시뮬레이터·에뮬레이터 실행은 생략하고 PR에 이유를 적습니다.

## 공개 확인과 변경 경과

- 코드 병합, 빌드, 업로드·처리, 테스트 배포, 심사, 정식 공개를 각각 기록합니다.
  병합·로컬 빌드 성공·스토어 업로드·TestFlight 배포만으로 정식 공개를 완료 처리하지 않습니다.
- iOS와 Android의 정식 공개 여부·공개일은 각각 확인합니다.
  한 플랫폼만 공개되면 다른 플랫폼은 확인된 진행 상태로 남깁니다.
  서버 단독 배포는 모바일 영역을 `해당 없음`으로 표시하고 서버의 실제 배포 상태·시각을 기록합니다.
