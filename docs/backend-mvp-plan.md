# 허투루 백엔드 MVP 구현 계획

## 1. 문서 목적

허투루 PRD의 MVP 범위를 기준으로 현재 Clipback 백엔드의 구현 상태를 정리하고, 프론트엔드가 안정적으로 연동할 수 있는 백엔드 완성 순서와 단계별 완료 기준을 정의한다.

이 문서는 백엔드 작업만 다룬다. 화면 구성, Flutter 상태 관리, OS 공유 화면 UI 등 프론트엔드 구현은 범위에서 제외한다.

## 2. MVP 백엔드 목표

백엔드는 다음 사용자 흐름을 지원해야 한다.

1. 사용자가 게스트 세션을 생성한다.
2. Instagram 등에서 공유한 링크 또는 직접 입력한 링크를 저장한다.
3. 링크에서 제목과 설명을 추출한다.
4. AI가 기본 카테고리와 사용자 카테고리 중 하나를 추천한다.
5. 적합한 카테고리가 없거나 추천에 실패하면 `미분류`로 저장한다.
6. 사용자는 저장된 콘텐츠를 최신순 또는 카테고리 필터로 조회한다.
7. 콘텐츠 상세에서 요약, 출처, 카테고리와 원본 링크를 확인한다.
8. 스크린샷을 업로드하고 저장된 이미지를 상세에서 확인한다.
9. 저장, 필터 사용, 카드 클릭, 재열람과 원본 링크 열기 이벤트를 기록한다.

## 3. 구현 원칙

### 3.1 저장 우선

메타데이터 추출, AI 추천 또는 OCR이 실패해도 유효한 콘텐츠 자체는 가능한 한 저장한다. 외부 연동 실패는 기본 제목·요약 또는 `미분류` fallback으로 처리한다.

### 3.2 사용자 데이터 격리

콘텐츠, 사용자 카테고리, 이벤트와 업로드 자산은 인증된 현재 사용자 범위 안에서만 조회하고 변경할 수 있어야 한다.

### 3.3 하나의 저장 파이프라인

OS 공유와 링크 직접 입력은 입력 방식만 다르고 저장 이후 처리 과정은 같아야 한다. URL 검증, 정보 추출, 카테고리 결정, 콘텐츠 저장과 이벤트 기록 로직을 공통 서비스로 구성한다.

### 3.4 외부 연동 방어

URL 요청, AI, OCR과 파일 저장에는 timeout, 응답 크기 제한과 실패 fallback을 적용한다. 외부 응답을 신뢰하지 않고 형식과 권한을 백엔드에서 다시 검증한다.

### 3.5 관찰 가능한 동작

핵심 행동과 fallback 사유를 이벤트로 남겨 PRD의 재열람률, 저장 완료율과 카테고리 추천 품질을 측정할 수 있어야 한다. 공유 원문, AI 프롬프트 전체와 민감 정보는 이벤트에 저장하지 않는다.

## 6. 단계별 구현 계획

## 6.1 1단계: 게스트 인증과 사용자 격리

### 목적

모든 요청이 사용자 ID `1`로 처리되는 임시 구조를 제거한다. 사용자 카테고리를 AI 추천 후보로 안전하게 사용하려면 인증과 소유권 검증이 먼저 완료되어야 한다.

### 작업

- `POST /api/v1/auth/guest`에서 실제 게스트 사용자를 DB에 생성한다.
- 생성된 사용자 ID를 subject로 가진 JWT access token을 발급한다.
- Bearer token을 검증하고 현재 사용자 ID를 반환하는 dependency를 구현한다.
- 만료, 변조, 형식 오류와 누락 토큰에 `401`을 반환한다.
- `GET /api/v1/users/me`가 실제 현재 사용자 정보를 반환하도록 변경한다.
- 콘텐츠, 카테고리, 피드, 업로드와 지표 API에 동일한 인증 dependency를 적용한다.
- 다른 사용자의 콘텐츠와 카테고리에 접근할 수 없는지 검증한다.

### 완료 기준

- 게스트 세션을 두 번 생성하면 서로 다른 사용자와 토큰이 생성된다.
- 각 사용자는 자신의 콘텐츠와 사용자 카테고리만 조회할 수 있다.
- 다른 사용자의 콘텐츠 ID로 상세·이벤트 API를 호출하면 정보가 노출되지 않는다.
- 잘못된 토큰으로 보호 API에 접근할 수 없다.
- 기존 공유 저장, 카테고리, 피드와 상세 테스트가 모두 통과한다.

### 권장 브랜치

`feature/backend-guest-auth`

## 6.2 2단계: 링크 정보 추출과 콘텐츠 enrichment (완료)

### 목적

고정된 `저장한 콘텐츠`, `요약 정보가 아직 없습니다.` 대신 사용자가 피드에서 콘텐츠를 식별할 수 있는 제목과 설명을 저장한다.

### 작업

- `MetadataClient`에서 HTML title, Open Graph title과 description을 추출한다.
- 직접 입력과 공유 저장이 같은 enrichment 서비스를 사용하도록 통합한다.
- 제목과 설명의 우선순위와 최대 길이를 정의한다.
- 설명이 없으면 안전한 fallback 요약을 사용한다.
- Instagram처럼 metadata 추출이 제한될 수 있는 플랫폼의 fallback을 정의한다.
- 외부 요청 실패가 콘텐츠 저장 실패로 이어지지 않도록 한다.

### URL 요청 보안

- `http`와 `https`만 허용한다.
- loopback, 사설 IP, link-local과 내부 네트워크 주소 접근을 차단한다.
- redirect 이후 주소도 동일하게 다시 검증한다.
- connect/read timeout을 적용한다.
- redirect 횟수와 다운로드 크기를 제한한다.
- HTML이 아닌 응답을 metadata 파싱 대상으로 사용하지 않는다.

### 완료 기준

- metadata가 있는 공개 링크는 추출된 제목과 설명으로 저장된다.
- metadata가 없는 링크도 기본값으로 정상 저장된다.
- timeout, 잘못된 HTML과 비정상 상태 코드가 저장 실패를 일으키지 않는다.
- 내부 주소와 지원하지 않는 URL scheme 요청이 차단된다.
- 공유 저장과 직접 입력에서 동일한 결과를 얻는다.

### 구현 결과

- Open Graph, Twitter와 HTML metadata 우선순위에 따라 제목과 설명을 추출한다.
- 내부 주소, 비표준 포트와 안전하지 않은 redirect를 차단한다.
- 일반 링크는 검증된 최종 redirect URL을 저장하고 Instagram 링크는 기존 정규화 URL을 유지한다.
- timeout, DNS·HTTP 오류, non-HTML, 응답 크기 초과와 metadata 부재는 기본 문구로 fallback한다.
- 직접 입력과 Instagram 공유 저장이 동일한 `ExtractionService`를 사용한다.

### 권장 브랜치

`feature/backend-content-enrichment`

## 6.3 3단계: AI 카테고리 자동 추천 (완료)

### 목적

사용자 입력 없이도 저장 콘텐츠를 기본 카테고리 또는 해당 사용자의 카테고리에 자동 분류하고, 적합한 후보가 없으면 `미분류`로 저장한다.

세부 정책은 [카테고리 자동 추천 정책 및 백엔드 구현 계획](./category-recommendation-policy.md)을 따른다.

### 작업

- 기본 카테고리와 현재 사용자의 카테고리를 추천 후보로 조회한다.
- `미분류`를 일반 추천 후보에서 제외한다.
- 제목, 설명, 공유 원문과 출처로 추천 입력을 구성한다.
- AI가 후보 category ID 또는 `null`을 구조화된 형식으로 반환하게 한다.
- 반환 ID가 실제 후보 목록에 포함되는지 다시 검증한다.
- 사용자 직접 선택이 있으면 AI 추천을 생략한다.
- 적합한 후보 없음, timeout, 오류와 잘못된 응답은 `미분류`로 처리한다.
- 할당 방식과 fallback 사유를 생성 이벤트 metadata에 기록한다.

### 완료 기준

- AI는 기본 카테고리와 현재 사용자의 카테고리만 선택할 수 있다.
- 사용자가 직접 선택한 카테고리가 항상 우선한다.
- AI는 새로운 카테고리를 생성하지 않는다.
- AI 실패가 저장 실패로 이어지지 않는다.
- 다른 사용자의 카테고리가 후보나 결과에 포함되지 않는다.

### 구현 결과

- `gpt-5.4-nano-2026-03-17`과 Responses API Structured Outputs를 사용해 후보 ID 또는 `null`만 반환받는다.
- 기본 카테고리와 현재 사용자의 카테고리만 후보로 전달하고 `미분류`와 다른 사용자의 카테고리는 제외한다.
- 사용자 직접 선택은 AI 호출 없이 복수 선택을 유지하며, 링크 자동 추천만 1개 카테고리를 할당한다.
- timeout, 입력 부족, 후보 없음, 거부·잘못된 응답과 API 오류는 모두 `미분류`로 fallback한다.
- 공유 원문은 URL 제거·공백 정규화·1,000자 제한 후 추천에만 사용하고 콘텐츠나 이벤트에는 저장하지 않는다.
- 생성 이벤트에는 할당 방식, 추천 ID와 제한된 실패 사유만 기록한다.

### 권장 브랜치

`feature/backend-category-recommendation`

## 6.4 4단계: 카테고리 수정과 콘텐츠 보정

### 목적

사용자가 AI 추천 결과를 변경하거나 `미분류` 콘텐츠를 나중에 분류할 수 있게 한다. 추천 품질도 실제 변경 행동으로 측정할 수 있다.

### 작업

- 콘텐츠의 카테고리를 교체하는 API를 추가한다.
- 현재 사용자에게 허용된 카테고리만 지정할 수 있게 한다.
- 카테고리 변경 이벤트와 변경 전·후 category ID를 기록한다.
- AI 추천 결과와 사용자 변경 여부를 분석할 수 있게 한다.

### 제안 API

```text
PUT /api/v1/contents/{content_id}/categories
```

### 완료 기준

- 사용자가 자신의 콘텐츠 카테고리를 변경할 수 있다.
- 다른 사용자의 콘텐츠나 카테고리를 사용할 수 없다.
- 변경은 콘텐츠 관계와 이벤트 기록을 하나의 트랜잭션으로 처리한다.

### 권장 브랜치

`feature/backend-content-category-update`

## 6.5 5단계: 스크린샷 업로드와 자산 저장

### 목적

PRD 핵심 범위인 사진 기반 콘텐츠를 실제 콘텐츠로 저장하고 상세 화면에서 다시 확인할 수 있게 한다.

### 작업

- 허용 이미지 MIME type과 최대 파일 크기를 정한다.
- 확장자가 아니라 파일 signature를 기준으로 이미지 형식을 검증한다.
- 파일명 충돌과 경로 조작이 불가능한 storage key를 생성한다.
- 로컬 개발 저장소와 운영 object storage 인터페이스를 구현한다.
- 스크린샷 `Content`와 `ContentAsset`을 생성한다.
- 파일 저장 실패 시 DB가 불완전하게 남지 않도록 보상 처리를 정의한다.
- 상세 응답에서 이미지를 확인할 수 있는 접근 URL 또는 별도 asset API를 제공한다.
- 업로드 응답을 placeholder 모델이 아닌 저장된 콘텐츠 정보 중심으로 변경한다.

### 완료 기준

- 유효한 이미지는 콘텐츠와 자산 레코드로 저장된다.
- 잘못된 형식과 제한 초과 파일은 저장되지 않는다.
- 사용자는 자신의 이미지 자산만 조회할 수 있다.
- DB 실패 시 불필요한 파일이 남지 않고, 파일 실패 시 콘텐츠가 생성되지 않는다.

### 권장 브랜치

`feature/backend-screenshot-storage`

## 6.6 6단계: OCR과 스크린샷 enrichment

### 목적

스크린샷에서 텍스트를 추출해 제목·요약과 카테고리 추천에 사용한다.

### 작업

- OCR 공급자 또는 로컬 OCR 구현을 선정한다.
- 이미지 bytes를 OCR에 전달하고 추출 텍스트를 정규화한다.
- OCR 텍스트로 제목과 요약을 생성한다.
- 카테고리 자동 추천 정책을 스크린샷에도 적용한다.
- OCR 원문 저장 여부와 보관 기간을 개인정보 관점에서 결정한다.
- OCR 실패 시 이미지 콘텐츠는 `미분류`와 기본 설명으로 정상 저장한다.

### 완료 기준

- 텍스트가 있는 스크린샷은 식별 가능한 제목 또는 요약을 가진다.
- OCR 결과를 사용해 허용된 카테고리 중 하나가 추천된다.
- OCR 실패가 업로드 저장 실패로 이어지지 않는다.

### 권장 브랜치

`feature/backend-screenshot-ocr`

## 6.7 7단계: 행동 이벤트와 성공 지표

### 목적

PRD의 핵심 지표인 재열람률과 보조 지표를 계산할 수 있도록 실제 사용자 행동을 DB에 기록한다.

### 작업

- placeholder `MetricsService`를 DB 기반으로 구현한다.
- 이벤트의 현재 사용자와 대상 콘텐츠 소유권을 검증한다.
- 다음 이벤트를 일관된 API 또는 도메인 서비스에서 기록한다.
  - `content_created`
  - `content_reopened`
  - `category_filter_used`
  - `card_clicked`
  - `original_link_opened`
- 이벤트별 필수 `content_id`, `category_id`와 metadata 규칙을 정의한다.
- 같은 사용자 행동이 중복 전송될 때의 허용 정책을 정한다.
- 원문 URL, 공유 텍스트와 민감 정보는 metadata에 저장하지 않는다.
- UT 분석에 필요한 집계 SQL 또는 운영 쿼리를 문서화한다.

### 측정 가능한 지표

- 콘텐츠 재열람률
- 사용자당 저장 수
- 첫 저장 완료 여부
- 카테고리 필터 사용률
- 콘텐츠 카드 클릭률
- 원본 링크 열기 비율
- AI 추천과 `미분류` 할당 비율

7일 리텐션과 저장 완료 시간은 세션 또는 클라이언트 이벤트 정의가 추가로 필요하므로 프론트 담당자와 이벤트 시점을 합의한다.

### 완료 기준

- 모든 이벤트가 인증된 사용자와 함께 DB에 저장된다.
- 다른 사용자의 콘텐츠에 대한 이벤트를 생성할 수 없다.
- 재열람률과 주요 행동 지표를 DB 쿼리로 계산할 수 있다.

### 권장 브랜치

`feature/backend-product-metrics`

## 6.8 8단계: API 통합 테스트와 운영 안정화

### 목적

프론트 연동과 UT 중 회귀를 줄이고 배포 가능한 백엔드 상태를 만든다.

### 작업

- FastAPI route, 인증 dependency와 실제 DB 경계를 포함한 API 통합 테스트를 추가한다.
- PostgreSQL 기준 migration upgrade와 `alembic check`를 CI에서 실행한다.
- backend 테스트, lint와 compile 검사를 GitHub Actions에 추가한다.
- health와 readiness endpoint를 구분하고 DB 연결 상태를 확인한다.
- 외부 연동 timeout과 fallback 발생을 구조화된 로그로 남긴다.
- 환경별 secret, database URL, AI/OCR/storage 설정을 문서화한다.
- 운영 CORS, 허용 업로드 크기와 요청 제한을 설정한다.
- API 오류 응답 형식과 주요 status code를 통일한다.

### 완료 기준

- PR마다 자동 테스트와 migration 검사가 실행된다.
- 새 DB에서 migration 후 주요 API E2E 테스트가 통과한다.
- 필수 설정이 없으면 서버가 명확한 오류로 시작을 중단한다.
- 외부 연동 실패 원인을 로그에서 구분할 수 있다.

## 9. PRD에서 결정이 필요한 항목

### 9.1 태그

PRD의 콘텐츠 카드에는 태그가 필수로 적혀 있지만, 현재 DB의 태그 테이블은 카테고리 구조 변경 과정에서 제거됐다. 태그가 독립적인 탐색 수단인지 단순 표시 정보인지 확정해야 한다.

권장안은 제목·요약·카테고리 기반 UT를 먼저 진행하고, 태그가 콘텐츠 식별에 실제로 필요한지 확인한 뒤 별도 기능으로 추가하는 것이다. MVP에 반드시 포함한다면 데이터 모델, AI 생성 규칙, 수정 API와 노출 개수를 별도로 정의해야 한다.

### 9.2 AI 추천 확인 방식

AI 추천 결과를 저장 전에 사용자에게 확인받을지, 자동 저장 후 사용자가 수정하게 할지 결정해야 한다. 백엔드 권장안은 자동 할당 후 수정 가능 방식이다. 저장 API가 한 번에 완료되고 추천 실패 시 `미분류`로 일관되게 처리할 수 있기 때문이다.

### 9.3 콘텐츠 처리 방식

MVP는 구현 복잡도를 줄이기 위해 동기 처리와 짧은 timeout을 사용한다. 저장 지연이 UT에서 문제가 되면 콘텐츠를 먼저 저장하고 enrichment 상태를 비동기로 갱신하는 방식으로 전환한다.

### 9.4 파일 저장소

로컬 개발은 filesystem을 사용할 수 있지만, 실기기 UT를 여러 환경에서 진행하거나 서버를 배포한다면 object storage가 필요하다. 운영 환경과 비용을 확인해 구현 전에 저장소를 선정해야 한다.

### 9.5 지원 플랫폼 확대

현재 공유 intake는 Instagram URL만 지원한다. YouTube와 TikTok 지원 순서는 UT 대상 콘텐츠 비중과 실제 share payload 확인 후 결정한다. 각 플랫폼은 payload 수집 → URL 정규화 테스트 → 저장 지원 순서로 추가한다.
