## Problem Statement

PR #75의 이미지 보관 기능을 병합하려 하지만 현재 main과 충돌하고, 카테고리 저장 재확인과 이미지 보관의 DB 마이그레이션 이력이 분기돼 있다. 기존 CI 성공만으로 현재 main과의 통합 안전성을 판단할 수 없다.

원본 저장을 기존 Volume으로 유지하더라도 새 백엔드의 이미지 삭제는 독립 삭제 기록이 필요하다. 그런데 초기화 도구는 배포 이미지에 포함되지 않았고, 실제로 쓰지 않는 DB·로그인·AI 설정까지 요구한다. 운영자는 어떤 준비를 마쳐야 자동 배포 후 기존 앱을 계속 사용할 수 있는지 명확한 실행·검증 절차가 필요하다.

## Solution

PR #75를 현재 main과 통합하고 마이그레이션 이력을 안전하게 합친다. 삭제 기록 초기화·검증을 필요한 Bucket 설정만으로 운영자용 Docker 이미지에서 실행할 수 있게 한다.

먼저 기존 Volume 저장을 유지하는 호환 버전을 배포한다. 코드 준비, 사용자 운영 준비, 별도 요청에 따른 병합, 배포 후 기존 앱 검증을 순서대로 수행한다. 신규 Bucket 저장 전환·정기 백업 운영·기존 이미지 이관은 후속 단계다. 이 명세는 기존 이미지 보관 정책을 대체하지 않는 보완 명세다.

## Implementation Decisions

- 기존 PR #75를 보완한다. 현재 main의 홈·마이 통계·카테고리 복구 계약을 유지하며 충돌을 해결한다.
- 카테고리 revision 202610250015와 이미지 revision 202610230018의 분기를 단일 head로 연결한다. 이미 배포된 revision의 부모 변경, 데이터 초기화, 검증 없는 stamp로 해결하지 않는다. 최종 head는 구현 결과로 기록한다.
- 기존 카테고리 제출별 처리 결과 보관 결정과 계정 격리를 유지한다. 이미지 통합으로 해당 기록이나 재확인 동작을 손상시키지 않는다.
- 운영자 이미지와 빌드 포함 목록에 초기화·검증 실행에 필요한 모듈을 포함한다. 기본 실행 진입점과 일회성 명령 실행 방법을 실제 이미지로 검증하고 문서화한다.
- 초기화·checkpoint 경로는 삭제 기록 설정만 읽고 DB engine·API 전체 설정에 의존하지 않도록 분리한다. 가짜 운영 비밀이나 운영 모드 검증 우회를 해결책으로 삼지 않는다.
- 초기화·checkpoint와 DB·원본 접근이 필요한 삭제 재처리를 분리한다. 재처리는 기존 필수 설정과 보호 동작을 유지한다.
- 사용자 Mac의 Docker에서 검증된 동일 이미지로 초기화·checkpoint를 실행한다. Docker 구동·Bucket 연결을 먼저 확인한다. 해당 실행에는 운영 DB·기존 Volume·원본/백업 Bucket 접근이 필요 없다.
- 새 namespace만 명시적 초기화한다. 기존 기록이 있는 환경의 재초기화나 기록 손실을 정상 초기화로 처리하지 않는다.
- 비밀값은 보호된 환경 파일로 제공한다. API에는 독립 삭제 기록 설정을 제공하고 백업 키는 제공하지 않는다.
- 첫 배포는 STORAGE_BACKEND=local과 기존 STORAGE_ROOT·Volume을 유지한다. 기존 자료는 삭제 가능한 테스트 자료지만 이번에는 호환성 검증용으로 유지한다. DB 초기화·일괄 삭제를 하지 않는다.
- 삭제 기록 준비는 병합·호환 배포 전에 완료한다. API의 자동 초기화로 대체하지 않는다.
- 에이전트는 코드·테스트·설정 안내를 준비한다. 사용자는 Bucket 생성, 콘솔 설정 입력, Mac 초기화·검증, 참여자 점검 안내를 수행한다.
- 설정 변경의 배포 발생 여부와 시점을 확인한다. 실제 초기화 결과와 최종 PR 상태 확인 후 별도 병합 요청에 따라 병합한다.
- 코드 준비 완료와 운영 배포 완료를 구분한다. 운영 체크리스트는 실제 배포 커밋·마이그레이션·기능 검증 결과를 남긴다.
- 기능 검증 실패 시 테스트 재개와 Bucket 전환을 보류한다. 적용된 DB와의 호환성을 확인하지 않은 이전 버전 복귀나 초기화를 하지 않는다.

## Testing Decisions

- 사용자와 합의한 경계는 기존 실제 PostgreSQL·HTTP API 통합 테스트와 실제 빌드한 Docker 이미지의 CLI 실행이다. 내부 함수 호출 순서나 모듈 구조보다 외부 동작·저장 결과·종료 상태를 검증한다.
- 기존 PostgreSQL repository/API 통합 검사, 이미지 삭제 통합 검사, 저장소 클라이언트 검사, 합성 데이터를 사용하는 Docker 배포·복구 검증 방식을 확장한다.
- 빈 DB와 카테고리/이미지 양쪽 분기에서 실제 업그레이드한다. 대표 기존 자료와 카테고리 제출 기록을 넣고 단일 head 도달, 데이터 보존, 스키마 일치와 기능 동작을 확인한다.
- local 이미지의 인증된 저장·원본 재조회·삭제 후 접근 차단을 API에서 검증한다. 삭제 기록 저장·검증이 실패하면 논리 삭제를 성공 처리하지 않는 기존 보호를 유지한다.
- 운영자 이미지 자체에 필요한 도구가 들어 있는지 실제 실행으로 검증한다. 삭제 기록 Bucket 설정만 제공하고 무관한 DB·로그인·AI 설정 없이 초기화·checkpoint가 성공해야 한다.
- 기존 namespace와 손상/누락된 기록, 연결·권한 오류를 검증한다. 실패를 성공 종료로 숨기거나 기존 기록을 덮어쓰지 않아야 한다.
- 삭제 재처리는 기존 DB·원본 설정 요건을 유지하는지 확인한다.
- 기존 홈 최초 불러오기·마이 통계·카테고리 복구의 앱 통합 회귀 검사를 유지한다. 새 화면 디자인이나 별도 UI 구현은 추가하지 않는다.
- S3 호환 대역과 Docker 합성 검증은 실제 Railway 권한·연결·데이터 검증의 대체가 아니다. 실행하지 못한 검사는 미실행으로 명시한다.
- 최종 PR 커밋의 CI와 코드 리뷰를 확인한다. 이전 PR head의 성공은 재사용하지 않는다.
- 운영 체크리스트: 새 ledger 초기화·checkpoint → 점검 및 API 설정 → 별도 병합 → 실제 migration·배포 커밋·readiness → 기존 앱의 이전 이미지 열람·새 저장/재조회·검증용 이미지 삭제/접근 차단 → 삭제 기록·영속 정리 상태 확인 → 테스트 재개.
- readiness 성공만으로 기능 정상이나 물리 정리 완료를 판단하지 않는다. 이미지 접근 권한과 원본 바이트를 실제 확인하고 검증에 쓰지 않은 자료까지 삭제하지 않는다.

## Out of Scope

- 신규 원본 Bucket 저장 활성화, 기존 이미지 이관과 Volume 사본 삭제.
- 정기 백업·보존 정리·알림 스케줄 구축 및 운영 격리 복원 실행.
- 백업·삭제 재처리를 위한 기존 Volume 접근 실행 환경 구축. 초기화용 Mac 컨테이너로 이를 해결했다고 간주하지 않는다.
- 새 앱 출시, 새 UI/UX, 이미지 보관 한도·품질·게스트·캐시 정책 변경.
- 운영 데이터 초기화, 기존 삭제 기록 재초기화, 과거 migration 이력 재작성.
- 이슈 작성이나 코드 준비 완료만을 근거로 한 PR 자동 병합 또는 운영 설정 변경.
