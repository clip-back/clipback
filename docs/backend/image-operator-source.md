# 운영 원본의 비공개 읽기

기존 API Volume을 옮기지 않고 별도 운영자 이미지에서 원본을 백업하는 경로다. 이 문서는 실행 방법이며 실제 Railway 연결·백업 성공 증거는 아니다. 최초 수동 백업 명령과 권한은 [백업·복구 안내](backup-recovery.md)를 따른다. 전체 점검·Mac 복원은 [첫 운영 실행 체크리스트](image-operator-first-run.md) 순서로 진행한다.

## 준비와 권한

API에 기존 Volume·STORAGE_ROOT·저장 backend를 유지한다. API에는 백업 Bucket 키를 공급하지 않는다. 운영자의 원격 읽기에는 Railway SSH 자격이 필요하지 않다.

실제 Volume과 기존 원본을 확인한 운영자가 식별자를 정하고 한 번 등록한다. 등록 명령은 존재하는 절대 디렉터리에만 작은 식별 파일을 생성한다. 기존 식별자를 바꾸거나 빈 경로를 자동 생성하지 않는다. API 이미지에는 이 준비 도구가 포함된다.

```sh
python -m scripts.image_source register --root /data/screenshots --source-id "$SOURCE_ID" --confirm-volume
```

`SOURCE_ID`는 영문·숫자·밑줄·하이픈 1~100자다. 실제 확인 없이 등록하거나 서버 재시작 시 자동 실행하지 않는다. 등록 결과를 잃어도 재등록하지 말고 기존 값과 원본 연결부터 확인한다. `.clipback-source-id`는 사용자 이미지가 아니며 외부 읽기 대상으로 제공하지 않는다.

API에 다음 환경변수를 제공하면 별도 운영자 리스너가 켜진다.

| 설정 | 의미 |
| --- | --- |
| `OPERATOR_SOURCE_ID` | 등록한 원본 식별자 |
| `OPERATOR_READ_KEY` | 앱 토큰과 다른 읽기 전용 비밀값, 최소 16자 |
| `OPERATOR_PORT` | 기본 9001, 공개 API PORT와 다른 포트 |
| `OPERATOR_HOST` | 기본 `::`; 환경의 내부 IPv4/IPv6 주소 계열에 맞춰 검증 |
| `STORAGE_ROOT` | 기존 실제 Volume의 원본 디렉터리 |
| `SCREENSHOT_MAX_BYTES` | 기존 기본 10MiB; 저장된 원본보다 낮추면 해당 백업은 실패 |

포트 설정 자체가 비공개 접근의 증거는 아니다. Railway 공개 도메인과 TCP 프록시는 기존 공개 API 포트만 가리켜야 한다. 운영자 포트에 공개 도메인·프록시를 추가하지 않는다. 공개 앱 라우터에는 운영 경로를 등록하지 않는다.

## HTTP 계약과 운영자 설정

별도 포트는 전용 읽기 키를 Bearer 인증하고 `X-Source-ID`로 기대 원본을 확인한다. `GET /source`는 등록 상태를 확인하고, `POST /source/read`는 JSON의 `storage_key`에 해당하는 원본만 반환한다. 응답의 식별자·크기·SHA-256을 클라이언트가 검증한다. 파일 키는 URL이나 접근 로그에 넣지 않는다. 운영자 리스너의 접근 로그는 비활성화한다.

인증 실패는 403, 기대 식별자 불일치는 409다. 실제 식별 파일 부재·불일치 또는 원본 연결 오류는 503이며 유효한 원본에서 요청한 파일만 없는 경우 404다. 절대 경로·상위 경로·심볼릭 링크·특수 파일·식별 파일은 읽을 수 없다. 삭제·업로드·임의 명령 실행은 제공하지 않는다.

별도 운영자 이미지에는 기존 최소 DB·삭제 기록·백업 설정과 함께 아래 값을 공급한다.

- `OPERATOR_SOURCE_URL`: 같은 Railway 환경의 API 내부 주소와 운영자 포트. 예시는 `http://<API의 실제 내부 호스트>:9001`이며 콘솔의 실제 값을 확인한다. 사용자 정보·query·fragment·추가 경로가 없는 URL만 허용한다.
- `OPERATOR_SOURCE_ID`, `OPERATOR_READ_KEY`, `SCREENSHOT_MAX_BYTES`: API와 같은 값.
- `STORAGE_ROOT`: 명시적인 절대 경로 설정은 유지하되 원본 mount로 오인하지 않는다. 원격 설정이 있으면 `local` 자산은 전부 원격 클라이언트로 읽고 빈 로컬 디렉터리로 대체하지 않는다. 기존 `s3` 자산은 원래 S3 클라이언트를 사용한다.

운영 `STORAGE_BACKEND=local` 백업은 원격 설정 세 값을 필수로 요구하며, 자산이 0개여도 생략할 수 없다. `s3` 모드에서도 원격 설정 없는 기존 `local` 자산 읽기는 거절한다. 직접 로컬 경로는 `test`·`local` 합성 실행에서만 허용한다. 원격 설정 세 값은 함께 제공해야 한다. 수동 작업 명령과 기존 직접 `create` 명령 모두 명시적 운영 runtime을 사용한다. 백업 준비와 게시에 동일한 원격 어댑터를 사용하며 원본 자산이 0개여도 원본 식별을 먼저 확인한다. 실패한 접속·권한·응답·크기/해시를 빈 정상 백업이나 삭제 완료로 처리하지 않는다. 백업 manifest의 `extra_file_count`는 원격 여분 파일을 열거한 증거가 아니며 0으로 원격에 여분 파일이 없다고 판단하지 않는다.

## 배포 시작과 실제 확인

공개 API와 운영자 리스너는 별도 프로세스로 실행한다. 운영자 앱은 공개 앱의 lifespan이나 요약 작업을 시작하지 않는다. 둘 중 하나가 조기 종료하면 감독 프로세스가 나머지도 종료하고 배포 실패로 보고한다. SIGTERM/INT에는 두 리스너를 종료하고 수거한다. 읽기 키가 없는 기존 배포는 공개 API만 실행한다.

실제 운영 전 확인 순서:

1. 기존 Volume과 원본을 직접 확인하고 식별자를 등록한다. 키·파일 내용은 보고서에 남기지 않는다.
2. 실제 내부 주소·주소 계열·포트로 운영자 서비스가 식별 확인·정상 원본 읽기를 수행하는지 확인한다.
3. 앱 토큰·잘못된 읽기 키·다른 식별자로 접근이 거절되는지 확인한다.
4. 공개 API의 `/source`가 404이며 공개 도메인/TCP 프록시에 운영자 포트가 연결되지 않았는지 확인한다. 공개 `/source` 404만으로 전체 배포의 포트 차단을 입증하지 않는다.
5. 운영자에 원본 Volume을 붙이지 않은 상태에서 수동 백업이 원본 바이트·크기·해시를 확인하는지 검증한다.
6. 실행/커밋·단계별 결과·오류 분류를 작은 보고서로 남긴다. 합성 Docker 성공을 실제 Railway 성공으로 표시하지 않는다.
