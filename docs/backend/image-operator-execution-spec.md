# 운영 원본 접근·첫 수동 백업·격리 복원 구현 스펙

## Problem Statement

운영자는 기존 Railway Volume의 이미지 원본을 보존하면서 저장소 전환에 앞서 실제로 복구 가능한 백업을 확보해야 한다. 현재 별도 운영자 컨테이너에 같은 경로를 지정해도 API에 연결된 Volume을 읽는다는 보장이 없다. 잘못된 빈 디렉터리를 정상 원본으로 오인하거나 파일 부재를 삭제 완료로 취급할 위험이 있다.

기존 정기 작업 명령에는 백업 외에 삭제 재처리·보존 정리가 함께 들어 있다. 기존 신규 이미지 저장 중단은 모든 업무 변경을 막지 않으며, 복원 명령의 쓰기 중단 확인 인자만으로 실제 중단을 증명할 수 없다. Mac 연결 단절·서버 재시작·시간 초과가 발생해도 운영 상태를 안전하게 확인하고 명시적으로 재개할 수 있어야 한다.

## Solution

Volume은 API에 유지하고, 같은 배포의 별도 비공개 포트에서 식별자와 전용 권한을 확인한 뒤 원본 읽기를 제공한다. 별도 Railway 운영자가 필요한 설정만으로 수동 백업을 실행하고 종료한다. 백업은 운영 DB·원본을 읽어 복구 지점을 생성하며 삭제 재처리와 보존 정리를 실행하지 않는다.

Mac에서 사전 준비와 로컬 전용 SSH 연결을 검증한 후 전체 업무 쓰기를 기술적으로 중단한다. 기존 작업의 종료를 최대 60초 기다려 확인하고, 최신 삭제 기록을 반영한 격리 복원 검증을 최대 30분 수행한다. 성공·실패 후 실행 종료와 운영 상태를 확인해 명시적으로 재개하고 임시 자료를 정리한다. 이번 완료 범위는 실제 원본 접근·수동 백업 1회·격리 복원·서비스 재개까지이며 저장소 전환 완료와 구분한다.

## Implementation Decisions

- **원본 보존:** 기존 계정 기반 원본 보관 ADR과 이미지 보관 정책을 유지한다. 원본은 변환하지 않으며 기존 Volume과 저장 경로를 유지한다. 기존 테스트 자료도 이번 검증에 사용하고 초기화하지 않는다.
- **원격 원본 읽기:** 기존 API 배포에 별도 비공개 리스너를 추가한다. 공개 앱 라우터에는 운영 경로를 등록하지 않는다. 동일한 애플리케이션 수명주기를 중복 시작하여 백그라운드 작업이 두 번 실행되지 않도록 한다. 내부 주소·주소 계열·포트 연결과 공개 도메인/TCP 프록시 미연결을 실제 배포에서 검증한다.
- **원본 식별:** 운영자가 실제 Volume 확인 후 식별자를 명시적으로 등록한다. 자동 등록·덮어쓰기·재시작 시 생성으로 확인 절차를 우회하지 않는다. 기대 식별자·원본 루트·파일 경로 범위를 검증하고 요청한 원본의 크기·해시를 확인한다. 연결 실패·권한 오류·잘못된 원본을 파일 없음이나 빈 정상 백업으로 처리하지 않는다.
- **권한 계약:** 앱 인증과 운영 인증을 분리하고 원본 읽기와 점검 제어 권한을 분리한다. 원격 운영 기능은 원본 확인·읽기와 명시적인 점검 시작·상태·재개로 제한한다. 임의 명령 실행·원본 삭제 기능은 제공하지 않는다. SSH 자격은 이 제한된 키와 별개인 넓은 권한임을 운영 문서에 명시한다.
- **백업 실행과 설정:** 별도 Railway 운영자 서비스는 PostgreSQL 18 도구를 포함하며 수동 작업 후 종료한다. 공개 도메인·정기 일정은 추가하지 않는다. DB·저장소·운영 권한 설정을 API 전용 AI·소셜 로그인 설정에서 분리한다. 테스트 모드나 가짜 비밀값으로 운영 설정 검증을 우회하지 않는다. API에는 백업 키를 공급하지 않는다.
- **명령 분리:** 수동 백업은 백업 생성만 수행한다. 기존 복합 작업의 삭제 재처리·보존 정리는 명시적인 별도 명령으로 분리하고 숨겨진 사전·사후 작업으로 실행하지 않는다. 해당 유지보수 명령도 점검 중 업무 변경 금지에 참여해야 하나 실제 운영 가동은 후속 범위다.
- **일관성:** 기존 DB 스냅샷·삭제 기록 체크포인트·원본의 물리 삭제 보호를 유지한다. 원본 읽기 어댑터는 백업 준비·검증·게시 전체에 일관되게 적용한다. 정상 백업의 기존 일관성 보호를 전체 서비스 점검으로 대체하지 않는다. 완료 표시 전 필요한 원본과 백업 산출물을 검증한다.
- **점검 상태:** 실행 식별자와 함께 점검 요청·종료 대기·쓰기 중단 확인·재개 결과를 영속적으로 식별한다. 단순 프로세스 메모리 플래그나 연결 종료 시 풀리는 DB 잠금만으로 점검 상태를 표현하지 않는다. 여러 프로세스에 걸친 새 작업 진입 차단과 진행 중 작업 종료 확인이 원자적으로 협력해야 한다. 상태를 확인하지 못하면 업무 변경을 허용하지 않는다.
- **차단 범위:** 일반 앱 API는 GET을 포함해 503을 반환한다. API 요청, 응답 뒤의 작업, 요약 작업의 시작부터 최종 반영, 삭제·이관 등 운영 명령의 업무 변경을 함께 보호한다. 진행 중 작업을 강제로 성공·실패 처리하지 않는다. 업무 DB·원본·삭제 기록의 변경이 중단 대상이며 점검 제어 기록·운영 로그·격리 대상 쓰기는 제외한다. health 및 점검 중 readiness는 업무 자료 변경을 유발하지 않아야 한다. 수동 DB 수정 등 협력하지 않는 외부 쓰기는 운영 체크리스트로 금지한다.
- **점검 진입:** 신규 진입을 차단한 뒤 최대 60초 동안 진행 중 작업의 종료를 기다린다. 완료 전 쓰기 중단을 선언하지 않는다. 초과 시 점검 진입 실패를 보고하고 복원을 금지하며 차단을 유지한다. 서버 재시작·작업 종료·연결 상실·시간 경과는 자동 재개 사유가 아니다.
- **복원 제어:** 기존 단순 쓰기 중단 확인 인자만을 신뢰하지 않고 실제 점검 상태와 실행의 유효성을 검증한다. 복원 중 필요한 삭제 기록 잠금과 최신 기록 검증을 유지한다. DB 스키마 변경이 필요하면 기존 자료를 보존하는 마이그레이션으로 제공한다. 세부 테이블·엔드포인트 이름은 구현에서 결정하되 이 외부 동작 계약을 유지한다.
- **Mac 연결:** Railway SSH의 로컬 전달은 127.0.0.1로만 바인딩한다. 운영자 경로와 복원 보호용 운영 DB에 필요한 연결만 사용하고 공개 포트를 새로 열지 않는다. SSH 자격은 Mac에 두며 서버 백업 서비스에 공급하지 않는다. 설치 CLI와 최신 문서의 차이를 확인하고 필요한 업데이트·키 등록 및 Docker 연결 설정을 실행 전에 검증한다. Docker 설정만으로 격리 복원 대상에 운영 연결 자격을 불필요하게 전달하지 않는다.
- **복원 준비·제한:** 가능한 이미지 준비·백업 다운로드를 점검 전에 완료한다. 쓰기 중단 확인 후 전체 복원 검증에 30분 예산을 적용하며 단계마다 새 예산을 부여하지 않는다. 선택한 복구 지점·최신 삭제 기록·점검 상태를 다시 검증한 후 격리 환경에서 원본 접근과 삭제 반영을 확인한다. 운영 DB나 원본을 복원 대상으로 사용하지 않는다.
- **실패·재개:** 연결 단절·시간 초과·검증 오류는 검증 중단과 실패 보고로 이어진다. 후속 작업이 뒤늦게 성공으로 결과를 바꾸지 않도록 종료를 확인한다. 실행 종료·잠금 해제·운영 상태 확인 뒤 권한 있는 운영자가 명시적으로 재개한다. Mac 없이 Railway 측에서 같은 제한된 제어를 수행하는 복구 절차를 제공한다. 실행이 남아 있거나 확인할 수 없으면 안전한 재개 완료로 표시하지 않는다. 30분은 전체 점검 시간 상한이 아니다.
- **정리·증거:** 실행 소유권을 식별하는 임시 디렉터리·컨테이너·연관 자원을 사용하고 성공·실패 시 정리한다. 비정상 종료 후 잔여 자원도 식별 가능해야 한다. 정리 대상은 해당 실행의 자원이며 운영 원본과 백업 복구 지점은 제외한다. 보고서는 백업/실행 식별자, 커밋·도구 버전, 단계별 성공 여부·오류 분류·해시 검증·재개 및 정리 결과를 담고 비밀값·사용자 본문은 제외한다. 대용량 사진·영상은 기본 증거로 요구하지 않는다.

## Testing Decisions

- 사용자가 승인한 경계는 기존 실제 PostgreSQL + API 통합 테스트와 실제 빌드 Docker 이미지의 운영 명령 실행이다. 내부 클래스 구조·함수 호출 순서보다 HTTP 응답, 업무 자료 변화, 원본 바이트, 명령 종료 상태와 보고서로 검증한다.
- 기존 이미지 저장 제어·삭제 통합 테스트를 확장한다. 실제 별도 DB 연결과 프로세스에서 신규 진입과 진행 중 변경을 경쟁시켜 점검 진입, 60초 제한, 작업 완료 대기, 재시작 후 유지, 명시적 재개와 실패 시 보호를 검증한다. HTTP 대역이나 단일 메모리 상태로 분산 쓰기 차단을 입증하지 않는다.
- 일반 앱 요청의 503, 정상 서비스 회귀, 원본 읽기/점검 제어 권한 분리, 앱 토큰 거절, 잘못된 식별자·경로·파일·해시 오류와 비공개 리스너 분리를 검증한다. 백그라운드 작업의 늦은 반영, 연결 단절과 재개 경쟁을 포함한다.
- 기존 Docker DB 덤프·Bucket 백업·격리 복원·삭제 기록 반영·다중 사용자 복원 테스트와 실행별 정리 도구를 재사용한다. 실제 PostgreSQL 18과 빌드 이미지로 원본 원격 읽기부터 새 복구 지점·최신 삭제 기록 적용·원본 열람까지 검증한다. S3 대역은 로컬 계약 검증이며 실제 Railway 증거와 구분한다.
- 백업 실행 전후 대기 중 삭제와 기존 백업이 유지되는지 확인하여 삭제 재처리·보존 정리의 비실행을 검증한다. 불필요한 AI·소셜 비밀값 없이 운영자 명령이 동작하고, 필수 설정 부재는 명확한 실패로 종료해야 한다.
- 터널 단절·점검 상태 확인 실패·60초 및 30분 예산·프로세스 종료·정리 실패를 시험한다. 자동 재개 금지, 늦은 성공 금지, 실행 소유 자원만 정리, 비밀값 없는 실패 보고를 확인한다. 제한 시간 시험은 검증 가능한 시간 제어를 사용하되 실제 프로세스 종료와 잠금 해제 검증을 생략하지 않는다.
- 코드 완료 증거는 테스트 환경·커밋·실제 실행한 선택형 Docker 검사를 기록한다. 실행하지 않은 검사는 통과로 기록하지 않는다. 새 스키마가 있다면 기존 DB 업그레이드·자료 보존도 실제 DB로 검증한다.
- 운영 완료는 별도 체크리스트로 증명한다: 실제 Volume 확인/등록 → 내부망 원본 읽기와 공개 차단 → Mac 터널·Docker 연결 → 서버 수동 백업 1회 → 점검 진입과 종료 대기 → 격리 복원 → 명시적 재개와 기존 앱 동작 → 임시 자원 정리. 각 단계의 보고서와 실패 내역을 남긴다.

## Out of Scope

- 신규 이미지 저장 backend의 Bucket 전환, 기존 이미지 이관 및 Volume 사본 삭제.
- 일일 백업·정기 실행 스케줄·삭제 재처리·보존 정리의 실제 가동. 기존 일일 백업·7일 복구 목표 자체는 유지한다.
- 원격 원본 삭제, 임의 운영 명령 실행 API, API에 백업 키 부여.
- 새 앱 점검 화면, 캐시 삭제, 기능별 부분 점검 정책.
- 실제 운영 DB에 대한 복원, 자동 장애 조치, 자동 점검 해제.
- 다른 공급자 백업, 새 비용 상한 정책, 비용 자동 차단·알림 서비스.
- 본 스펙 게시만으로 배포·CLI 업데이트·키 등록·실제 점검·백업·복원을 실행하는 것.

## Further Notes

- 설계 인터뷰 Q1~Q17과 검증 경계 확인을 모두 사용자 승인받았다. 문서는 계획 확정이며 구현·배포 성공 증거가 아니다.
- 앞선 운영 확인 시 PostgreSQL은 18.6, 기존 원본은 local이었다. 자산 수·배포 커밋·접속 상태는 실행 직전에 재확인한다. Bucket 생성이나 목록 조회 성공을 백업 쓰기·복원 성공으로 간주하지 않는다.
- 실제 운영 완료에는 사용자 환경의 비밀값 공급·연결·점검 및 재개 확인이 필요하다. 코드 구현만 완료된 경우 해당 상태와 미완료 운영 항목을 분리해 보고한다.
- 저장소 전환이나 정기 가동은 이번 운영 검증 결과를 확인한 뒤 별도 단계로 진행한다. 실패한 검증을 근거로 전환하지 않는다.
