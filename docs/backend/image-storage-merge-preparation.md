# 이미지 보관 PR 병합 준비

상태: 2026-10-25 사용자 최종 확인으로 준비 계획 확정. PR #75의 코드 수정·병합·운영 설정은 아직 실행하지 않았으며, 이번 확인은 계획 확정이다.

## 확정한 방향

- 먼저 기존 Volume 저장을 유지한 호환 버전을 병합·배포한다. 이후 신규 Bucket 저장 전환, 기존 자료 이관을 별도 단계로 확인한다.
- 현재 이미지와 콘텐츠는 삭제해도 되는 테스트 데이터지만, 이번에는 유지해 기존 이미지 열람·삭제 등 호환성 검증에 사용한다. DB 초기화나 일괄 삭제는 하지 않는다.
- 준비·배포·동작 확인 중 짧은 점검 시간을 허용한다. 테스트 참여자에게 이용 중단을 요청하고 확인 후 재개하는 계획이며, 아직 안내나 서버 중단을 실행하지 않았다.
- 병합 전에 삭제 기록 저장소와 초기화를 준비한다. 원본 저장이 local이어도 이미지 삭제는 삭제 기록을 필요로 한다.
- 운영자용 이미지에 삭제 기록 초기화·검증 도구를 포함하고 실행 명령을 문서화하는 코드 보완을 병합 전 작업으로 계획한다. 아직 구현하지 않았다.
- 초기화·검증은 삭제 기록 Bucket 설정만으로 실행하도록 분리한다. DB·원본을 사용하는 삭제 재처리 명령의 설정 요건은 유지한다.
- 초기화는 사용자 Mac의 Docker에서 검증된 운영자용 이미지로 일회성 실행한다. Docker 구동·Bucket 연결을 먼저 확인하고, 키는 보호된 환경 파일에 사용자가 입력한다. 새 namespace만 초기화하고 이어서 checkpoint를 검증한다. 기존 namespace를 재초기화하지 않는다.
- 이번 상세 계획은 PR 병합과 기존 Volume 상태의 배포 검증까지다. 신규 Bucket 저장·정기 백업·기존 자료 이관은 후속 단계로 두며, 준비 전에는 신규 Bucket 저장을 켜지 않는다. 일일 백업·7일 복구 정책은 유지하되 실제 작업·복원 검증 전에는 운영 중이라고 표시하지 않는다.

## 확인한 병합 장애물

- PR #75의 head `4979761c8309af039d96cb1e08e35b7afdcaee7b`는 main과 충돌한다. 기존 CI 5개 성공은 충돌 해결 후 통합 검증을 대신하지 않는다.
- 현재 main과 PR의 마이그레이션 분기를 합친 뒤 단일 head로 검증해야 한다.
- 삭제 기록 초기화 명령의 실행 환경을 마련해야 한다. 백업 작업의 기존 Volume 접근 경로는 후속 전환 단계의 선행 조건으로 남긴다.

## 역할과 중단 기준

- 에이전트: 코드 충돌 해결, 마이그레이션 분기 통합, 운영자 이미지 보완, 테스트, 설정명·실행 순서·검증 결과 정리.
- 사용자: Railway 콘솔에서 삭제 기록 Bucket 생성과 환경변수 입력, Mac Docker 초기화·검증 명령 실행, 테스트 참여자 점검 안내.
- 기존 이미지 열람·저장·삭제 중 하나라도 검증에 실패하면 테스트 재개와 Bucket 전환을 보류하고 수정 후 재검증한다.
- 적용된 DB 상태와의 호환성을 확인하지 않은 과거 버전 복귀나 DB 초기화는 하지 않는다.

## 확정한 실행 순서

1. 에이전트가 main 충돌과 마이그레이션 분기를 해결하고 초기화 도구·이미지·실행 문서를 보완한다. 배포된 migration 이력은 임의 변경하지 않는다.
2. 통합 코드의 회귀 테스트, 양쪽 migration 분기에서 단일 head로의 업그레이드, 운영자 이미지의 최소 설정 초기화·검증을 확인한다. PR 최종 커밋의 CI와 코드 리뷰를 확인한다.
3. 사용자가 비공개 삭제 기록 Bucket을 생성하고 Mac에서 새 namespace 초기화·checkpoint 검증을 완료한다. 비밀값은 채팅·Git·로그에 기록하지 않는다.
4. 사용자가 점검을 안내하고 API의 삭제 기록 설정을 적용한다. 기존 Volume과 STORAGE_ROOT=/data/screenshots, STORAGE_BACKEND=local을 유지한다. 설정 변경으로 별도 배포가 발생할 수 있으므로 적용 시점을 확인한다.
5. 준비 증거와 최종 PR 상태를 확인한 뒤 별도 병합 요청에 따라 병합한다. 자동 배포에서 실제 migration 성공·배포 커밋·readiness를 확인한다.
6. 기존 앱으로 이전 이미지의 권한 있는 열람, 새 이미지 저장·재조회, 검증용 이미지 삭제 후 접근 차단을 확인한다. 삭제 기록과 영속 정리 작업 상태도 확인한다. readiness 성공만으로 기능 검증을 대체하지 않는다.
7. 확인이 모두 끝나면 테스트를 재개한다. 실패하면 점검을 유지하고 수정·재검증한다. 신규 Bucket 저장은 켜지 않는다.

## 후속 단계의 착수 조건

- 신규 원본 Bucket과 별도 백업 Bucket, 권한·실제 연결 검증.
- 기존 local 원본에 실제 접근할 수 있는 백업·물리 삭제 재처리 실행 경로와 운영 스케줄. 초기화용 Mac 컨테이너는 이 경로를 대신하지 않는다.
- 일일 백업·보존 정리·실패 알림과 실제 격리 복원 검증.
- 신규 Bucket 저장 검증 후 새 앱 배포와 기존 자료 이관. 이관만으로 기존 Volume 사본을 제거하지 않는다.

다음 작업은 코드 보완 단계다. 구현은 후속 요청에 따라 시작하며, 운영 설정은 위 역할 분담대로 진행하고 PR 병합은 준비 완료 후 별도 요청에 따른다.
