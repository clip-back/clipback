# 이미지 운영 도구의 원본 접근과 백업·복원 실행 계획

> 이 문서는 구현 전 확정한 설계 이력이다. 현재 운영 상태와 실행 명령은
> [첫 운영 실행 체크리스트](image-operator-first-run.md)를 따른다.
> 아래 daily/maintain의 삭제 재처리 결합 설명은 설계 당시 기준이며 현재 구현은 분리돼 있다.


상태: 2026-10-26 Q17 사용자 최종 승인으로 실행 계획 확정. 설계 인터뷰를 완료했다. 제품 코드·운영 설정 변경과 실행은 별도 요청으로 진행한다.

## 확정한 방향

- 첫 완료 범위는 실제 원본 접근, 수동 백업 1회, 격리 복원 성공이다. 신규 Bucket 저장 전환·기존 이미지 이관·정기 실행은 결과 확인 후 이어간다.
- 이후 정기 백업·삭제 재처리는 사용자 Mac이 꺼져 있어도 동작하는 서버 측 환경을 기준으로 설계한다. Mac은 수동 점검·격리 복원에 사용할 수 있지만 정기 작업의 상시 실행 기반으로 삼지 않는다.
- 첫 수동 백업은 원본·DB를 읽어 새 백업을 만드는 작업으로 한정한다. 원본 삭제 재처리와 오래된 백업 정리는 별도 명령으로 분리하고, 삭제 기록에 따른 복원 보호는 유지한다.
- 첫 격리 복원은 Mac Docker에서 수행한다. 필요한 DB 백업·원본 이미지의 Mac 임시 보관을 허용하되 저장소 밖의 접근 제한된 위치를 사용한다.
- 기존 Volume은 API에 유지하고 별도 서버 운영자가 인증된 제한적 원격 경로로 실제 원본 위치를 확인한 뒤 읽는다. API에 백업 키를 주지 않는다. 첫 실행 범위는 읽기이며, 접속 실패·잘못된 Volume을 파일 부재로 처리하지 않는다.
- 첫 격리 복원 검증 동안 운영 자료를 변경하는 동작 전체를 기술적으로 중단한다. 신규 이미지 저장뿐 아니라 콘텐츠 삭제·계정 변경·백그라운드 작업을 포함한다. 실제 중단을 확인한 뒤 검증하고 종료 후 명시적으로 재개한다. 참여자 안내나 기존 이미지 pause만으로 중단을 입증하지 않는다.
- Mac 복원 검증의 성공·실패 후 이번 실행이 만든 임시 DB·이미지 사본·컨테이너를 정리하고 비밀값 없는 결과 보고서만 남긴다. 운영 원본과 백업 Bucket의 복구 지점은 정리 대상이 아니다. 정리 실패와 비정상 종료 후 남은 자원은 실행별로 식별해 보고한다.
- 검증 실패·연결 끊김에는 검증을 중단한다. 실행 종료·잠금 해제·운영 상태를 확인한 뒤 운영자가 쓰기를 명시적으로 재개한다. 시간 경과만으로 자동 재개하지 않으며 Mac 연결을 잃어도 서버 측 상태 확인·재개 경로를 제공한다. 실패한 검증 결과로 이관·저장소 전환을 진행하지 않는다.
- 원격 원본 읽기는 기존 API 배포 안의 별도 포트에서 제공하고 Railway 내부 주소로 접근한다. 앱 토큰과 다른 전용 키로 인증한다. 공개 앱 API에 해당 경로를 포함하지 않고 원본 위치 확인·읽기만 제공한다. 삭제·임의 명령 실행은 제외하며 실제 내부 연결과 공개 접근 차단을 검증한다.
- 첫 격리 복원 점검 중 일반 앱 API는 조회를 포함해 503으로 제한한다. 운영자 상태 확인·원본 읽기·복원에 필요한 조회·health는 별도 유지한다. 새 점검 화면은 만들지 않고 기존 오류·재시도 화면을 사용하며 기기에 이미 표시된 내용을 지우지 않는다.
- 점검 진입은 신규 요청·변경 작업 차단 후 이미 시작한 요청·백그라운드 작업의 종료를 최대 60초 기다린다. 종료 확인 전에는 쓰기 중단 완료로 판정하지 않는다. 시간 초과 시 검증을 시작하지 않고 차단 상태를 유지하며 명시적 재개를 요구한다. 재시작만으로 점검 상태가 풀리지 않는다.
- 원본 Volume에 전용 식별자를 명시적으로 등록하고 운영자가 기대하는 식별자와 일치할 때만 읽는다. 등록은 실제 Volume 확인 후 별도 준비 단계로 수행한다. 식별자 부재·불일치 시 중단하고 자동 생성하지 않는다. 파일 누락·읽기 실패·크기 또는 해시 불일치는 백업 실패다.
- 별도 Railway 운영자 서비스에서 첫 백업을 수동 실행하고 완료 후 종료한다. PostgreSQL 18 도구를 사용하며 공개 도메인·정기 실행 일정은 추가하지 않는다. DB·저장소·운영자 설정만 요구하고 AI·소셜 로그인 비밀값 요구를 분리한다. 실행 비용은 실제 사용량으로 확인한다.
- Docker 이미지 준비·백업 다운로드 등 가능한 준비는 점검 전에 완료한다. 쓰기 중단 확인 후 복원 검증은 최대 30분으로 제한하며 시작 전 백업·최신 삭제 기록·점검 상태를 다시 검증한다. 시간 초과 시 검증을 중단하고 실패로 보고한다. 정리·종료·운영 상태 확인 후 명시적으로 재개하므로 30분은 전체 점검 시간의 상한이나 자동 재개 시점이 아니다.
- 자동 백업용 원본 읽기 권한과 사람의 점검 시작·상태 확인·재개 권한을 분리한다. 백업 키만으로 점검 상태를 변경할 수 없다. 점검 제어는 비공개 운영 경로의 제한된 명령으로 제공하고 임의 명령 실행·원본 삭제는 제외한다. Mac 연결 상실 시 Railway 측에서도 같은 제어 명령으로 확인·재개할 수 있도록 준비한다. 비밀값은 채팅·Git에 남기지 않고 각 실행 환경에 공급한다.
- Mac은 Railway SSH 터널로 비공개 운영자 경로와 복원 보호용 운영 DB에 연결한다. 로컬 전달 포트는 127.0.0.1에만 바인딩하고 새 공개 도메인·DB 공개 포트는 만들지 않는다. CLI 업데이트·명령 지원과 Docker에서의 실제 연결을 점검 전에 검증한다. SSH 자격은 사람의 Mac 수동 연결에만 사용하고 서버 백업 서비스에는 공급하지 않는다. 연결 단절 시 검증 실패·점검 유지 원칙을 적용한다. CLI 업데이트·키 등록·Docker 설정 변경은 이후 운영 준비 단계에서 수행한다.
- 기존 합의인 원본 보존, 일일 백업·최근 7일 복구 목표, 독립 삭제 기록, API에 백업 키 미제공, 테스트 자료 유지 정책은 변경하지 않는다.

## 확인한 현재 상태

- 운영 API는 PR #75 병합 버전이며 DB head는 202610250019다. PostgreSQL 18.6, 원본 경로는 /data/screenshots다.
- 앞선 읽기 전용 점검에서 DB의 local 자산 18개와 Volume 파일 18개를 확인했다. 실행 직전에 수량과 상태를 다시 확인해야 한다.
- 삭제 기록 초기화·checkpoint·API 설정은 사용자가 완료했다고 알렸다. 원본·백업 Bucket도 생성했다. 원본 Bucket 목록 조회는 성공했지만 쓰기·삭제 권한은 아직 검증하지 않았다.
- 기존 API 이미지에는 운영자 도구가 없다. 별도 컨테이너에 같은 경로를 지정하는 것만으로 실제 Volume 접근이 보장되지 않는다.
- 현재 daily/maintain은 삭제 재처리를 포함한다. 잘못된 로컬 경로의 파일 부재를 실제 삭제 완료로 오인하지 않는 실행 경계가 필요하다.
- 설치된 Railway CLI 4.5.6과 현재 공식 문서의 명령 지원 범위가 다르다. 명령 지원·실제 연결 검증 없이 접근 경로가 준비됐다고 판단하지 않는다.

## 확정한 실행 순서와 완료 기준

1. 원본 원격 읽기·백업 전용 명령·최소 설정·점검 제어·Mac 복원 도구를 구현하고 검증한다. 운영 쓰기 중단은 서비스 DB·원본·삭제 기록의 업무 변경을 대상으로 하며 점검 제어 상태와 운영 로그 등 필요한 제어 기록은 허용한다. API·백그라운드 작업·운영 도구를 함께 보호하며 점검 중 수동 DB 변경 등 외부 쓰기도 금지한다.
2. PostgreSQL 18 운영자 이미지를 준비한다. 실제 Volume 확인과 식별자 등록, 내부망 읽기·권한 분리·공개 접근 차단·Mac 터널 및 Docker 연결을 검증한다. 연결 준비 전에는 점검을 시작하지 않는다.
3. 서버 운영자에서 수동 백업을 1회 실행한다. 기존 스냅샷·원본 보호 경계를 유지하며 삭제 재처리·보존 정리는 실행하지 않는다. 백업 생성 성공과 복원 검증 성공을 별도로 기록한다.
4. Mac에서 이미지·백업 다운로드 등 사전 준비를 마치고 점검에 진입한다. 일반 앱 API를 503으로 막고 진행 중 작업을 최대 60초 기다린다. 쓰기 중단 확인에 실패하면 복원을 시작하지 않는다.
5. 쓰기 중단 확인 뒤 선택한 백업·최신 삭제 기록·점검 상태를 다시 검증하고 최대 30분 동안 격리 복원한다. 원본 크기·해시·열람과 삭제 기록 반영을 확인한다. 성공·실패·연결 단절·시간 초과를 구분해 보고한다.
6. 실행 종료·잠금 해제·운영 상태를 확인하고 명시적으로 서비스를 재개한다. 이번 실행의 Mac 임시 사본·컨테이너를 정리하고 정리 실패도 보고한다. 보고서에는 비밀값·사용자 본문 없이 실행/백업 식별자, 검증 항목, 결과와 오류 분류를 남긴다.
7. 실제 원본 접근·수동 백업·격리 복원·명시적 재개와 정리 결과까지 확인해야 이번 단계를 완료로 판정한다. 코드·대역 테스트만으로 실제 Railway 운영 검증을 완료했다고 표시하지 않는다. 실패 시 정상 서비스 재개와 검증 재시도를 별개로 판단한다.

신규 Bucket 저장 전환·기존 이미지 이관·정기 실행·물리 삭제 재처리·보존 정리 가동은 후속 단계다. 이번 작업 완료를 전체 저장소 전환이나 일일 백업 운영 완료라고 표시하지 않는다.

인터뷰에서는 계획 문서만 작성한다. 실제 서비스 중단·파일 복사·백업·삭제·복원·저장소 전환은 실행하지 않는다.
