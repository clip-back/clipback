# 이미지 보관 운영 전환

이 문서는 코드 준비 후 운영자가 실행할 순서입니다. 로컬 합성 검증은 운영 Railway Bucket의
호환성·권한·백업 스케줄·실제 청구액을 증명하지 않습니다. 실제 실행 결과는
[통합 검증 이력](../history/2026-10-24-image-storage-integration.md)에 따로 기록합니다.

## 필요한 환경과 권한

| 실행 주체 | 필요한 접근 | 제공하지 않는 접근 |
| --- | --- | --- |
| API | DB, 현재 원본 Bucket, 이전 로컬 원본, 독립 삭제 기록 저장소 | 백업 Bucket 자격증명 |
| 백업·보존 작업 | DB, 두 원본 위치, 삭제 기록, 별도 백업 Bucket | 앱 사용자에게 전달하는 자격증명 |
| 복원·이관 운영자 | 검증할 복구 지점과 최신 삭제 기록, 격리 Docker, DB major에 맞는 도구 | 검증 도구를 통한 운영 서비스 자동 개방 |
| 앱·공유 확장 | Clipback API 세션, 서버가 허용한 짧은 원본 접근 정보 | S3 접근 키·백업 권한 |

API의 S3 변수와 `DELETION_LEDGER_S3_*`는 서로 다른 비공개 Bucket을 가리켜야 합니다.
백업 자격증명은 API 환경에 넣지 않고 0600 운영자 설정 파일로 별도 공급합니다.
일반 API 이미지에는 운영자 스크립트가 포함되지 않습니다. 실제 공급자의 자격증명 범위·삭제 권한을
직접 점검해야 하며, 별도 Bucket 이름만으로 권한 분리가 증명되지는 않습니다.

구체적 설정은 [저장소 운영](image-storage-operations.md), [삭제 기록](image-deletion.md),
[백업·복원](backup-recovery.md)의 현재 계약을 따릅니다. API·작업 서비스가 같은 DB와 원본·삭제 기록을
사용하는지 확인합니다. 삭제 기록을 이미 사용 중인 환경에서 새 namespace로 초기화하지 않습니다.

## 전환 순서와 확인 기준

1. **호환 백엔드와 DB 확장**: 기존 원본 GET을 유지하는 이 버전을 먼저 배포하고
   `alembic upgrade head`를 실행합니다. 통합 head는 `202610250019`이며 기존 이미지·카테고리 분기를 함께 포함합니다. 새 원본 저장소를 바꾸기 전
   기존 `local` 자산이 권한 있는 사용자에게 같은 바이트로 열리는지 확인합니다.
2. **독립 삭제 기록과 작업 서비스 준비**: 새 환경만 명시적 초기화를 하고, 이미 사용한 기록은
   최신 head와 연결된 불변 기록을 검증합니다. API에 백업 키가 없는지 확인합니다. 원본 삭제 성공은
   독립 기록과 DB 논리 삭제 이후이며, 물리 정리는 영속 재시도 작업으로 남을 수 있습니다.
3. **신규 Bucket 저장 전환**: `STORAGE_BACKEND=s3`와 실제 공급자 endpoint·region·주소 방식을
   설정합니다. 합성 시험 계정으로 일반·iOS·Android 공유를 저장하고 크기·SHA-256·소유권,
   구버전 인증 GET과 새 access 응답을 확인합니다. 잘못된 설정을 운영자 중단으로 통제할 수 있어야 합니다.
4. **일일 백업과 복원 검증**: 실제 DB major에 맞는 운영자 이미지로 UTC 00:00 `daily`,
   매시간 15분 `maintain`을 예약하고 실패·미완료·기한 초과 결과를 알림에 연결합니다.
   DB와 원본을 함께 보관한 정상 지점으로 실제 격리 복원을 완료합니다.
5. **새 앱 배포**: API 호환성이 확인된 뒤 access 확인·직접 다운로드·기기 캐시를 사용하는 앱을
   배포합니다. 본앱과 네이티브 공유의 API base URL이 같아야 합니다. 앱 업데이트 전에도 기존
   인증 GET이 유지됩니다. 서명 URL에 Clipback 토큰을 보내지 않고 일반 로그에 서명 query를 남기지 않습니다.
6. **기존 자료 이관**: `image_migration inspect` 결과를 검토하고, manifest SHA에 묶인 정상 격리
   복원 보고서를 준비한 뒤 `apply`를 제한된 묶음부터 실행합니다. 중단 후 재실행해 미완료 자료만
   이어 옮깁니다. 기존 콘텐츠·자산 ID·계정·원본 바이트를 대조합니다. 자세한 명령과 실패 처리는
   [이미지 이관](image-migration.md)을 따릅니다.

기존 자료가 30MiB·300MiB를 넘어도 원본을 삭제하지 않습니다. 한도는 새 이미지에만 적용합니다.
이관 성공만으로 이전 로컬 사본을 일괄 제거하지 않습니다. 보존한 로컬 사본도 이후 사용자 삭제의
정리 대상이며, 이관 후에도 디스크 사용량 보고에 포함됩니다.

## 중단과 복구

`python -m scripts.image_storage_admin pause`는 이미 허용된 저장 완료를 기다린 뒤 신규 이미지를
막습니다. 기존 원본 열람·삭제와 완료된 공유 저장의 재전송은 유지됩니다. 원인을 해결한 뒤
`resume`으로 엽니다. 이미 보관한 원본·백업 비용은 저장 중단 뒤에도 발생합니다.

S3 자산이 생긴 뒤에는 S3를 읽지 못하는 과거 백엔드로 단순히 되돌리지 않습니다. 현재 호환 버전에서
신규 쓰기 중단 또는 설정 수정으로 대응하고, 원본 위치를 임의로 `local`로 일괄 되돌리지 않습니다.
대상 S3 복사·검증·DB 전환이 불확실한 이관은 영속 정리 기록과 실제 참조를 기준으로 재개합니다.

복원 시 운영 쓰기를 동결하고 **현재 살아 있는 삭제 기록**을 확보해 오래된 복구 지점에 적용합니다.
그 상태를 실제 사용자 개방 시점까지 유지해야 합니다. 기록이 없거나 최신 상태를 확인할 수 없으면
서비스를 열지 않습니다. `restore-check`는 격리 검사이며 운영 복원·동결·개방을 자동 실행하지 않습니다.
삭제 후 시험 계정에 원본이 남지 않은 경우는 타인의 원본이 남아 있어도 인증과 404를 확인하고 `image_get_skipped: true`,
`image_bytes_passed: false`로 기록합니다. 이를 원본 바이트 재조회 성공으로 바꾸어 보고하지 않습니다.

## 운영 목표 해석

최근 7일 복구 지점과 일일 백업은 작업이 정상 완료될 때의 목표입니다. 삭제 자료는 6일 여유 기간과
시간별 정리로 최대 7일 이내 백업 참조와 불필요한 사본을 제거하도록 설계했습니다. 작업 실패가
지속되면 기한을 넘을 수 있으며 미완료·기한 초과를 실패로 다뤄야 합니다. 삭제 기록은 필요한
이전 복구 지점이 남은 동안 유지합니다. 불변 해시 원본을 여러 지점이 참조하므로 매일 전체를
중복 복사하지 않습니다.

운영 보고는 계정 논리 사용량, 로컬·Bucket 원본의 물리 사용량, 백업 사용량, 관측한 전송을 구분합니다.
Bucket 직접 다운로드·백업 전송·삭제 기록 비용 등 미관측 값은 `null`이며 0원이 아닙니다.
실제 공급자 사용량·청구서와 함께 월 1만 원의 설계 목표를 판단합니다. 서버·DB·AI 비용은 별도이고
자동 금액 차단이나 서비스 전체 비용 상한은 없습니다.

동일 Railway 계정·공급자 전체 손실, 악의적인 전체 삭제 기록 rollback, 실패가 지속된 뒤의 일일
복구 목표는 이 구조가 보장하지 않습니다. 실제 OAuth·실기기·외부 송신 앱·운영 이관·운영 스케줄은
각 환경에서 별도로 확인합니다.
