# 운영 격리 복원을 위한 점검 제어

이 기능은 일반 앱 API와 백그라운드·운영 작업의 업무 변경을 함께 막는 제어다. 신규 이미지 저장만 막는 기존 `image_storage_admin pause`와 구분한다. 실제 운영 실행·서비스 중단은 별도 운영 요청과 준비 확인 뒤 진행한다.

## 적용과 상태

기존 DB는 추가 마이그레이션 `202610260020`을 먼저 적용한다. 기존 업무 자료를 초기화하지 않으며 최초 점검 상태만 `open`으로 만든다. 애플리케이션 재시작은 점검 상태나 작업 기록을 초기화하지 않는다.

일반 API 요청은 조회·인증·원본 접근을 포함해 작업 진입 기록을 먼저 남긴다. 응답 본문·스트리밍·응답 후 작업이 모두 종료된 뒤에만 제거한다. 요약 작업은 작업 확보부터 외부 대기와 최종 반영까지 같은 기록으로 보호한다. 수동/일일 백업·보존 정리·삭제 재처리·이관·이미지 저장 중단/재개 명령도 같은 경계를 따른다. 기존 잠금을 얻기 전에 진입하고, 업무 잠금·트랜잭션이 종료된 뒤 기록을 제거한다.

점검 요청은 `open → draining → frozen` 순서다. `draining`부터 새 일반 요청은 503 `service_maintenance`로 거절된다. 진행 중 작업의 종료를 최대 60초 기다린다. DB/잠금 대기·연결 오류도 이 한도를 연장하지 않으며, 완료를 확인하지 못하면 검증을 시작하지 않는다. 최초 요청의 영속 기한이 지나면 후속 조회·재시작·재요청으로 대기 시간을 갱신하거나 늦은 `frozen` 성공을 만들지 않는다.

`frozen`은 DB·원본·삭제 기록의 업무 변경 중단을 뜻한다. 제어 기록·운영 로그·격리 복원 대상 쓰기는 허용한다. health와 점검 상태·원본 읽기·복원 필수 조회는 유지한다. 점검 중 readiness는 업무 자료를 기록하지 않고 기존 디렉터리 존재·DB·Bucket 읽기 준비 상태만 확인한다. PostgreSQL 내부 WAL 같은 엔진 동작을 완전히 중단한다는 의미는 아니다.

수동 DB 수정이나 수정 전 운영 스크립트 등 이 경계를 따르지 않는 외부 쓰기는 점검 동안 금지한다. 배포 전 기존 프로세스를 종료하고 같은 통합 버전을 사용한다.

## 비공개 제어와 권한

원본 읽기 키와 다른 `OPERATOR_CONTROL_KEY`를 API의 비공개 운영 리스너에 공급한다. 두 키가 같으면 설정을 거절한다. 제어 키는 최소 16자이며 줄바꿈을 포함할 수 없다. 앱 로그인 토큰이나 읽기 키로 점검 상태를 변경할 수 없다. 공개 앱 포트에 제어 경로를 등록하지 않는다. 원본 삭제·임의 명령 실행은 제공하지 않는다.

제어에는 API의 `DATABASE_URL`도 필요하다. 원본 읽기만 설정한 기존 리스너는 DB 제어 설정 없이 계속 읽기만 제공한다. DB나 상태 확인 실패는 성공으로 숨기지 않는다. API에는 백업 키를 공급하지 않는다.

비공개 제어 경로는 다음과 같다. 모든 요청은 제어 키의 Bearer 인증을 사용하고 본문·응답에 사용자 콘텐츠나 비밀값을 기록하지 않는다.

| 경로 | 동작 |
| --- | --- |
| `GET /maintenance` | 현재 단계·실행 ID·세대·종료 대기 기한·작업 기록 확인 |
| `POST /maintenance/start` | 새로운 UUID `run_id`로 신규 진입 차단 시작 |
| `POST /maintenance/drain` | 같은 실행의 기존 작업 종료 대기, 성공 시 `frozen` |
| `POST /maintenance/resume` | 작업·복원 기록이 없음을 확인한 명시적 재개 |
| `POST /maintenance/recover` | 실행 종료를 확인한 특정 잔여 작업 기록 복구 |
| `POST /maintenance/restore/start` | `frozen`과 실행/세대 확인 후 복원 작업 등록 |
| `POST /maintenance/restore/finish` | 복원 실행 종료·잠금 해제 확인 뒤 작업 종료 기록 |

작업 ID·종류·실행자는 상태 조회에서 확인한다. 복구/복원 종료는 `operation_id`와 `executor_stopped: true`라는 명시적 확인이 필요하다. 복원 시작은 등록된 실행의 세대를 확인하며, 등록 중에는 서비스 재개를 거절한다. 복원 도구는 실제 자식 프로세스와 Docker 자원을 종료하고 원본 잠금을 해제한 뒤에만 종료 확인을 전송해야 한다. 단순 요청 종료·SSH 연결 상실만으로 확인을 전송하면 안 된다.

## 서버 측 명시적 재개

Mac을 잃었을 때도 API 또는 검증한 운영자 이미지에서 아래 제한된 명령을 실행할 수 있다. 이 명령은 `DATABASE_URL`만 요구하며 AI·로그인·원본/백업 키를 요구하지 않는다. DB 자격과 명령은 해당 실행 환경에 공급하며 채팅·Git에 넣지 않는다.

```sh
python -m scripts.maintenance status
python -m scripts.maintenance start --run-id <새 UUID>
python -m scripts.maintenance resume --run-id <현재 실행 UUID>
```

`start`는 신규 진입 차단 후 같은 실행의 종료 대기까지 수행한다. 실패해도 차단은 유지된다. 기한이 지난 실행은 복원을 금지하고 명시적 재개 뒤 새 UUID로 다시 시작한다. 상태 확인에 실패했다면 쓰기가 안전하게 중단됐거나 재개됐다고 판단하지 않는다.

비정상 종료·취소된 `to_thread` 쓰기는 Python 대기가 끝난 뒤에도 남을 수 있다. 따라서 작업 기록을 자동 만료하거나 서버 시작 때 제거하지 않는다. 실제 실행자와 관련 스레드·자식 프로세스가 종료되어 뒤늦은 변경이 불가능한지 확인한 뒤 **해당 기록만** 복구한다.

```sh
python -m scripts.maintenance recover --run-id <현재 실행 UUID> \
  --operation-id <확인한 작업 UUID> --confirm-executor-stopped
```

이 명령도 서비스를 자동 재개하지 않는다. 잔여 복원 자원과 잠금 해제·운영 상태를 확인하고 별도 `resume`을 실행한다. 실행 상태를 확인할 수 없다면 재개 성공으로 처리하지 않는다.

## 백업·복원과 제어 기록

점검 제어 테이블은 업무 스냅샷 비교에서 제외한다. 덤프에는 그대로 포함할 수 있으나, 격리 복원 도구가 생성한 DB 사본에서만 작업·제어 기록을 초기화한 뒤 복원된 API를 시작한다. 이 초기화는 임의 대상 DB 인자를 받지 않으며 운영 DB에 수행하지 않는다. 기존 이미지 저장 제어 등 다른 업무 테이블은 제외하거나 초기화하지 않는다. 예전 복구 지점도 계속 읽을 수 있어야 한다.

단순 `--writers-frozen` 확인만으로 복원 검증을 시작하지 않는다. 후속 격리 복원 명령은 영속 점검 실행·세대·복원 기록과 최신 삭제 기록을 확인해야 한다. 30분 제한·Mac 터널·실제 복원 동선은 다음 티켓에서 연결하며 이 제어 구현만으로 실제 운영 복원을 완료했다고 표시하지 않는다.

신규 삭제 기록 namespace 초기화는 기존 Bucket 전용 설정을 유지한다. 활성화 전의 오프라인 준비 작업이며 점검 중 활성 namespace를 변경·재초기화하지 않는다. 원본 식별자 등록도 운영자가 Volume을 확인한 별도 준비 단계로 수행한다.
