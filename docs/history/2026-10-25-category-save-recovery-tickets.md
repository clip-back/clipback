# 카테고리 생성·수정 입력 보존과 실패 복구 구현 티켓 분할

## 기준과 승인

- 요청: `to-tickets`로 [스펙 #86](https://github.com/clip-back/clipback/issues/86)을 구현 티켓으로 나누고 선행 관계를 정리한다.
- 기준: `docs/category-save-recovery`, 시작 HEAD `a6166c1`, 작업 트리는 clean이었다.
- #86의 최신 본문 전체·댓글·하위 이슈·선행 관계를 조회했다. 댓글과 기존 하위 이슈는 없었으며
  본문은 [로컬 구현 스펙](../frontend/category-save-recovery-spec.md)과 일치했다.
  원본 본문의 SHA-256은 `aab5ba59aff919015db68ebfa8c55d4b41d652f40a7a751e855ff2fe07c28f76`이다.
- 사용자가 게시 전 초안 5개의 크기·본문·선행 관계와 #86 하위 이슈 생성, `ready-for-agent` 라벨·기본 선행 관계 연결을 승인했다.
- 첫 생성 경로에 필요한 비동기 결과 전달·API·최소 처리 기록을 함께 연결하고, 그 경계를 바탕으로 수정·목록 복구를 나눴다.
  각 티켓은 앱/HTTP 또는 서버/DB에서 독립 시연·검증 가능한 동작이며 플랫폼 실행 증거를 포함한다.

- #88↔#89, #90↔#91 사이에는 직접 선행 관계를 두지 않았다. 파일을 함께 수정할 가능성은 구현상 조율 대상이며
  서로의 완료가 필요하다는 이유로 해석하지 않았다.
- 진행 가능한 묶음은 `#87 → (#88·#89) → (#90·#91)`이다. 이 기록 시점에서 바로 시작할 수 있는 티켓은 #87이다.
  모든 선행 이슈가 닫힌 뒤 다음 묶음이 열린다. 실제 진행 때 최신 상태·담당자를 다시 조회한다.

## 확인한 결과와 범위

- 게시 전 원본 스펙의 변경 여부·기존 하위 이슈를 다시 확인했다. 각 이슈 생성 직후 번호·제목·본문·라벨·부모·상태·선행 관계를 읽어 검증했다.
- 승인한 초안에서 선행 항목만 기본 관계로 옮겼으며, 게시용 본문과 GitHub 본문 전체가 정확히 일치했다.
- 부모 #86의 본문·제목·라벨·OPEN 상태는 게시 전후 동일하다. 하위 관계 외 부모 본문 수정·댓글 추가·종료는 수행하지 않았다.
- 초안 5개의 템플릿·선행 순서·순환 없음·스펙 스토리 60개의 분담을 확인했다. 게시 결과는
  `/private/tmp/clipback-86-tickets/publication.json`과 각 이슈 조회 JSON에 보존했다.
- 문서 작업으로 제품 코드·테스트·DB 마이그레이션·iOS/Android 실행은 수행하지 않았다.
  각 티켓의 검증 수용 조건은 앞으로 구현하면서 실행할 계획이며 이번 결과로 대체하지 않는다.
