# 카테고리 생성·수정 입력 보존과 실패 복구 구현 명세 작성

## 요청과 기준

- 요청: `to-spec`으로 확정한 정책·디자인을 구현 스펙으로 정리하고 GitHub Issues에 게시한다.
- 작업 브랜치: `docs/category-save-recovery`. 시작 HEAD는 정책 확정 커밋 `ac3ecfa`이고 작업 트리는 clean이었다.
- 제품 조사 기준은 main `d98d2b32f276d271efd613f4d0447168304a88cd`다.
  현재 용어집·ADR·정책과 API·시트·기존 검증 경계를 확인했으며 제품 구현은 진행하지 않았다.
- 현재 명세: [카테고리 생성·수정 입력 보존과 실패 복구 스펙](../frontend/category-save-recovery-spec.md).

## 검증 경계 확인

- 사용자는 실제 앱+HTTP 대역+메모리 세션 저장소와 FastAPI HTTP+실제 PostgreSQL의 두 기존 통합 테스트 경계를 승인했다.
- 앱은 실제 시트의 입력 유지·10초·재확인·계정 변경·조회 전용 재시도를, 서버는 중복 실행·반영과 결과 기록·응답 유실·계정 격리를 검증한다.
- iOS Simulator·Android Emulator의 키보드·뒤로가기·드래그·스크롤·글자 확대와 플랫폼별 변경 전/후/Figma 비교를 포함한다.
- 이 확인은 `to-spec`의 “Check with the user that these seams match their expectations.” 지침에 따른 것으로,
  확정한 제품 정책을 다시 인터뷰한 것이 아니다.

## 작성한 계약과 범위

- 지정한 7개 섹션과 사용자 스토리 60개로 정책·디자인·API·기록 보관·검증·제외 범위를 정리했다.
- 기존 생성·수정 요청의 호환성을 유지하면서 선택적 제출 키와 종결 결과 메타데이터를 추가하는 계약을 구체화했다.
  새 키로 바꾸지 않는 재확인, 업무 거절과 미확인의 구분, 변경과 결과 기록의 원자성, 이후 수정·삭제 보존을 포함한다.
- ‘결과 다시 확인’의 원래 저장 실행 가능성과 ‘다시 불러오기’의 카테고리 조회 전용 동작을 구분했다.
- 명세 본문에는 특정 구현 파일 경로나 코드 예제를 넣지 않았다. 코드 위치·조사·게시·실행 이력은 본 기록과 기존 설계 이력에서 관리한다.

## 게시와 문서 검증

- 트래커는 `clip-back/clipback` GitHub Issues이고 라벨은 `ready-for-agent`다.
- 기존 카테고리 제목 이슈를 읽기 전용 검색했으며 같은 명세를 찾지 못했다. 라벨 존재도 확인했다.
- 일반 샌드박스의 `gh` 요청은 네트워크 연결에 실패했고, 승인된 네트워크 경계에서 읽기 전용 요청을 정상 완료했다.
- [GitHub 이슈 #86](https://github.com/clip-back/clipback/issues/86)을 `[Spec] 카테고리 생성·수정의 입력 보존과 실패 복구` 제목과
  `ready-for-agent` 라벨로 생성했다. 생성 뒤 다시 조회해 OPEN 상태·제목·라벨과 로컬 본문 전체의 정확한 일치를 확인했다.
- 게시한 본문의 SHA-256은 `aab5ba59aff919015db68ebfa8c55d4b41d652f40a7a751e855ff2fe07c28f76`이다.
- 필수 7개 섹션·사용자 스토리 60개의 연속 번호, 구현 파일 경로·코드 블록 미포함을 확인했다.
  변경 문서 4개의 상대 링크 118건·로컬 앵커·줄 끝 공백 검사에서 문제가 없었다.
- 이번 작업은 문서 작성이므로 제품 테스트·DB 마이그레이션·iOS/Android 실행을 하지 않는다.
  명세의 검증 계획을 실제 실행 결과로 보고하지 않는다.
