### Standards

- 과거 API 이미지의 embedded probe가 새 모듈을 요구하던 문제를 제거했다. 실제 과거 API 이미지 revision `0fb05dcd3112b4581ca2ff565970f680341ed10a`로 PostgreSQL 16·18 복원을 재현 후 2개 통과를 확인했다. 새 이미지로 과거 형식만 읽은 검사와 구분한다.

## 자원 정리와 남은 작업

이번 검증이 만든 컨테이너·네트워크·볼륨을 실행 소유권 기준으로 정리했다. 통합 테스트용 PostgreSQL/S3 컨테이너 2개와 중간 이미지 태그 7개도 제거했다. 최종 검증 이미지 2개와 비밀값 없는 작은 결과 기록을 보존했다. 대용량 사진·영상은 생성하지 않았다.

작업용 관리 체크아웃 6개는 Codex 앱의 보관 기능을 사용했으나 정리되지 않았다. 5개는 다른 활성 작업이 사용 중이라는 오류, 현재 대화의 체크아웃은 primary checkout 제거 불가 오류였다. 약 200MiB이며 임의 파일 삭제로 관리 상태를 우회하지 않았다. 모든 구현 내용은 통합 브랜치에 커밋돼 있다.

실제 운영 실행은 [첫 실행 체크리스트](../backend/image-operator-first-run.md)에 남긴다. #98~#101은 코드 구현·통합 증거로 종료했으며, #102와 부모 #97은 실제 원본 확인·수동 백업·점검·격리 복원·명시적 재개·정리의 운영 증거 전까지 열린 상태로 유지한다.

실제 Railway 배포/설정 변경, Volume 식별 등록, SSH 키 등록·CLI 업데이트, 서비스 점검, 운영 백업/복원은 실행하지 않았다. 신규 Bucket 저장 전환·기존 이미지 이관·정기 실행·물리 삭제 재처리·보존 정리 가동도 후속 단계다.

## PR #103 Linux CI 후속 수정

첫 원격 실행 `40263793889`에서 일반 검사 5개는 통과했지만 운영자 복원 묶음은
`2 failed, 16 passed, 12 errors`였다. 호스트 소유의 0600 백업 설정을 root 컨테이너에서
읽어 소유자 검사에 실패했고, root API 컨테이너가 생성한 0600 local 원본을 호스트
운영자가 읽지 못했다. Docker Desktop의 파일 공유와 달리 Linux bind mount는 이 소유권
차이를 그대로 드러냈다.

합성 테스트의 운영자 2곳과 혼합 local/S3 원본을 만드는 API 1곳에 호스트 UID/GID를
명시했다. 운영 코드의 0600·소유자 검사와 실제 원본 읽기 권한을 완화하지 않았다.
기존 실패 시나리오 전체를 다시 실행하며, 최종 원격 결과는 PR #103의 해당 커밋 CI로 확인한다.

두 번째 원격 실행 `40264624434`에서는 앞선 오류가 사라지고 복원 묶음 29개가 통과했다.
남은 1개는 잘못된 원본 식별자를 주입하는 테스트에서 root 등록 명령이 만든
`.clipback-source-id`를 호스트가 수정할 수 없는 `PermissionError`였다. Linux tmpfs에서
실제 등록 CLI 실행 후 UID 1001로 수정하는 최소 재현을 두 번 실행해 실패를 확인했다.
등록 UID만 1001로 바꾸면 같은 0600 모드·같은 경로에서 통과했다. 해당 테스트의 등록
컨테이너에도 호스트 UID/GID를 지정하며, 제품의 원본 식별 권한이나 보호 동작은 변경하지 않는다.
