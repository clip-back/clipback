# 콘텐츠 자동 태그 (#433)

저장한 콘텐츠에 서버가 태그를 붙이는 작업의 이력입니다. [상위 이슈 #433](https://github.com/clip-back/clipback/issues/433)

## #435 시간별 정리와 격리 복원에서 고아 태그 제거

2026-11-20에 기준 커밋 `1e2e711`에서 구현을 시작했습니다. 링크·이미지 삭제와 이미지 삭제 기록 재적용은 고아 태그를 남겼습니다. 회원 탈퇴와 계정 삭제 기록 재적용은 계정의 태그를 CASCADE로 삭제했습니다. 로컬 `maintain` 연결에서 테스트 태그를 지울 수 있는지도 확인했습니다. [이슈 #435](https://github.com/clip-back/clipback/issues/435)

한 문장으로 정리하면, 그 문장의 스냅샷을 잡은 직후에 연결이 확정될 때 그 연결까지 지워지는 경합을 로컬 PostgreSQL에서 재현했습니다. 사용자 결정에 따라 PostgreSQL 기본 격리 수준인 `READ COMMITTED`의 한 트랜잭션에서 두 문장으로 정리합니다. 먼저 `FOR UPDATE SKIP LOCKED`로 후보를 잠그고, 다음 문장에서 연결을 다시 확인해 어디에도 붙지 않은 태그를 지웁니다. 저장 쪽은 마지막 조회에서 `FOR KEY SHARE`를 얻고, 그때 사라진 태그를 한 번 다시 만듭니다.

- 시간별 `maintain`은 복구 지점 보존 정리와 삭제 장부 파기를 마친 뒤 별도 트랜잭션에서 태그를 정리합니다. 결과는 `orphan_tags_deleted` 건수를 담고, 태그 정리 SQL이 실패하면 종료 코드 1입니다.
- 격리 복원은 모든 삭제 기록을 적용한 뒤 커밋 직전에 같은 두 SQL 문장을 실행합니다. 현재 재적용 스크립트가 과거 API 이미지 안에서 실행되므로 SQL 문자열을 유지하고 테스트로 두 사본을 비교합니다. [백업과 복원 운영 안내](../backend/backup-recovery.md)

## #436 태그 이름 정규화와 AI 응답 판정

## #437 저장 시 일반 링크와 스크린샷에 태그 추가

일반 링크의 저장 시 카테고리 추천과 스크린샷의 글자 읽기·사진 요약에 태그 칸을 추가했습니다. 기존 호출에서 태그를 최대 3개 받아 사용자 태그가 비어 있을 때 콘텐츠와 함께 저장합니다. 스크린샷에서는 글자 읽기 결과를 사용하며, 글자가 없거나 응답 전체가 실패하면 태그가 비어 있습니다. 인스타그램 게시물·릴스·TV와 유튜브 영상의 태그는 자동 요약이 맡으며, 반영은 #438 범위입니다. 저장 시 카테고리 추천의 출력 상한 기본값은 160입니다. ## 유튜브·인스타그램 자동 요약 완료 시 AI 태그 (#438)

유효한 자동 요약이 완료될 때, 잠근 콘텐츠의 태그가 비어 있으면 같은 모델 응답에서 받은 태그를 최대 3개 저장합니다. 처리 중 추가된 수동 태그를 보존하고, 삭제된 콘텐츠나 만료된 이전 작업의 응답은 반영하지 않습니다. 지원되는 인스타그램 링크는 저장 시 받은 추천 태그를 버리고 요약 완료 뒤 상세 조회에 태그를 표시합니다. [이슈 #438](https://github.com/clip-back/clipback/issues/438)

- 배포 전에 저장되어 대기하던 작업에도 배포 뒤 완료 시 적용합니다. 이미 처리가 끝난 콘텐츠를 다시 처리하지 않습니다. 마이그레이션이 없어 배포 전·후 작업 행 형식이 같아 따로 재현할 상태가 없습니다. 저장 직후 대기 상태와 작업 완료 뒤 상세 조회를 같은 통합 테스트에서 확인했습니다.
- 구현 `e90e3ac`에서 감독이 허용한 요청 스키마 기대값 변경은 Gemini·OpenAI의 `properties.tags`와 `required`의 `tags` 추가입니다. OpenAI의 필드에는 SDK가 만든 `title: Tags`를 포함합니다. 공급자 원시 응답에서 태그 칸 누락·비목록·혼합 목록이 기존 제목·요약·카테고리와 오류 판정을 바꾸지 않는지 확인했습니다.
- NUL(U+0000)이 든 태그를 공급자가 반환하면 PostgreSQL이 거부해 요약 완료까지 실패하는 것을 두 공급자 대역으로 재현했습니다. 감독 판단에 따라 공용 AI 태그 정리에서 해당 항목을 버립니다. #437의 저장 시 카테고리 추천과 스크린샷 글자 읽기에도 같은 규칙을 적용합니다. 범위 밖인 수동 입력은 로컬 `POST /api/v1/contents`의 `tag_names`에 NUL을 보내 HTTP 500을 한 번 확인했습니다.
- 검수 반영 `4df617b`에서 유튜브 카테고리 지시 바로 아래에 후보 JSON을 배치하고 작업자 건너뜀, 태그 칸의 null·숫자·객체, 앱 DEBUG 로그를 검사했습니다. 두 PostgreSQL 세션이 새 태그를 반대 순서로 삽입할 때 교착을 재현했습니다. 공용 저장소에서 입력 순서대로 태그 ID를 배정한 뒤 정규화 키 순서로 삽입해, 충돌하는 두 요청이 완료되고 기존 반환 순서와 표기가 유지되는 것을 확인했습니다.
- 시작 커밋 `6dda208`에서 기능 테스트 12건이 실패했습니다. 첫 커밋의 부분 검사에서 593건, 검수 반영 커밋에서 607건이 통과했습니다. 두 부분 검사 모두 Ruff 통과, 스킵 0건입니다. CHANGELOG는 #439에서 작성합니다.

## #439 실제 모델 표본과 자동 태그 업데이트 내역

- 같은 입력을 main 기준 `1e2e711`과 기능 브랜치 `4edacbf`에서 각각 저장해 유튜브·인스타그램·스크린샷·일반 링크 2쌍씩, 총 8쌍을 비교했습니다. 카테고리는 8쌍 모두 일치했습니다. 제목·핵심 한 줄의 유무는 8쌍, 요점의 유무는 8쌍에서 양쪽이 같았습니다.
- 모델 예산 30회 중 26회를 사용한 것으로 보수적으로 집계했습니다. 비교용 24회에 계수기가 놓친 최초 main 인스타그램 추천의 2초 시간 초과 시도 1회와 이미 시작된 자동 요약 1회를 포함했습니다. 시간 초과 저장은 비교에서 제외했습니다. 감독 판단으로 OpenAI SDK와 Gemini의 전송 경로를 가짜 응답으로 검증한 뒤 같은 2초 설정으로 다시 측정했고, 이후 추천 시간 초과는 0건이었습니다.

## #440 상세 '태그' 줄 넘침 확인과 '디자인 확인 필요' 기록

- 앱 코드를 바꾸지 않았으므로 변경 전·후·Figma 3장 비교는 하지 않았습니다(#433 결정 12). 대신 태그가 채워진 상세 '태그' 줄을 iOS·Android에서 글자 배율 1.0·1.3으로 촬영해 넘침을 확인했습니다.
