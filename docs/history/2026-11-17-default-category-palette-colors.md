## 변경과 영향

새 데이터 마이그레이션 `202611170023`(앞 리비전 `202611060022`)에서 기본 카테고리 템플릿과 기존 사용자의 기본 카테고리 중 이름과 옛 색이 모두 같은 행만 갱신한다. 색 비교는 대소문자를 무시한다. 과거 seed 마이그레이션은 유지하고 출력용 스크립트의 목록도 새 색으로 맞췄다.

| 이름 | 옛 색 | 새 색 |
| --- | --- | --- |
| 업무 팁 | #DC2626 | #FF6277 |
| 생활 꿀팁 | #D97706 | #FFA24B |
| 공부 | #059669 | #5BD89D |
| 취업 | #4F46E5 | #64B5F6 |
| 제품 추천 | #7C3AED | #B9AAFF |
| 장소 | #0891B2 | #FFD75C |

사용자가 고른 다른 색, 다른 이름에 붙은 옛 색, `is_default=False`인 사용자 카테고리, NULL 색은 유지한다. 미분류는 `#6B7280` 그대로다. 새 사용자는 실제 `seed_for_user`가 갱신된 템플릿을 복사한다. 앱 코드·응답 필드·8색 팔레트 값은 변경하지 않았다.

**병합 = 운영 배포, 기존 앱에 바로 보임.** 이 서버 변경이 병합·배포되면 앱 업데이트 없이 폴더와 배지가 새 저장 색을 사용한다. Figma의 연한·진한 배지 색 짝을 맞추는 앱 변경은 별도 범위다. 이번 기록에서 실제 운영 반영은 확인하지 않았다.

### 되돌리기 한계

`downgrade`는 이름·`is_default=True`·새 색이 같은 행을 옛 색으로 되돌린다. 마이그레이션 뒤 사용자가 같은 새 팔레트 색을 일부러 선택한 행도 함께 돌아간다. 이를 구분할 기록이 없다는 승인된 한계를 코드 주석과 테스트에 남겼다. 소문자 옛 색으로 저장됐던 행도 되돌린 뒤에는 대문자 옛 색으로 저장된다.

## 검수와 부분 검사

고정 구현 커밋 범위의 Standards·Spec 검수는 높음·중간·낮음 모두 0건이었다. 추가 코드 수정 없이 수용했다. 기존 계약 테스트는 승인된 취업 색 기대값 네 곳과 관측 주석만 바꿨으며, 미분류와 다른 응답 단언은 유지했다.

새 DB 테스트는 실제 PostgreSQL의 격리 schema에서 과거 마이그레이션을 적용한 뒤 새 리비전을 실행하고 저장된 색을 비교한다. 템플릿·기존 사용자 6색, 소문자 옛 색, 사용자 선택·다른 이름·사용자 카테고리·NULL·미분류 보존, 신규 사용자 복사, downgrade와 재업그레이드를 확인했다.

- 구현 전 DB 색 단언과 출력 스크립트 단언은 각각 의도한 옛 색 불일치로 실패했다.
- 구현 후 새 DB 테스트 7개, 출력 테스트 1개가 통과했다.
- 새 테스트와 허용된 계약 테스트 두 파일을 함께 실행한 결과: `249 passed in 71.64s (0:01:11)`, 종료 코드 0, skip 없음. 이는 구현 중 부분 검사다.
- 옛 색 조건·기본 카테고리 조건·대소문자 무시 조건을 각각 제거한 세 변형은 사용자 선택 색 보존·사용자 카테고리 보존·소문자 옛 색 갱신 단언에서 각각 종료 코드 1로 실패했다. 실행기는 세 실패 위치와 원본 복구를 확인하고 종료 코드 0으로 끝났다.
- 최초 변형 실행은 조건 삭제 후 남은 SQL 바인딩 때문에 색 단언 전에 중단됐다. 이 실패는 보호 조건 검증 근거에서 제외하고, 실험 준비를 수정한 뒤 위 세 변형을 다시 확인했다.

main 병합은 #412의 로그인 약관 링크·콜백·실패 문구를 포함했다. 전체 검사 전에 로그인 배치·약관 링크·문의하기·개인정보 링크·로그인 실패 이동의 소비자 테스트 5파일을 실행해 88개가 통과했고, `flutter analyze --no-pub`도 종료 코드 0이었다. 설계 변경은 없었다.

처음 main 반영 전 CHANGELOG 검사는 main의 선행 #412 항목 차이 때문에 실패했다. 시작 커밋과 현재 파일이 동일한 항목·값·종료 코드 1로 실패함을 비교한 뒤 이번 추가분만 확인했다. main 병합 후 기본 검사는 종료 코드 0이며, main 대비 CHANGELOG 변경은 미배포 항목 한 줄 추가뿐이다.

## 로컬 마이그레이션 왕복

합성 데이터만 담은 전용 PostgreSQL에서 `alembic upgrade head` → `alembic downgrade -1` → `alembic upgrade head`를 실행했다. 전체 종료 코드 0이며 각 단계 뒤 템플릿 7행과 기존 사용자 기본 카테고리 6행을 조회했다.

템플릿·사용자 6색 모두 첫 upgrade에서 위 표의 새 색, downgrade에서 옛 색, 재 upgrade에서 새 색과 일치했다. 공용 미분류는 세 단계 모두 `#6B7280`이었다. 운영 DB·실제 사용자 데이터는 사용하지 않았다.

## 전체 검사

문서 작성 전 위 검증 기준 커밋에서 수행한 전체 검사 결과다. 원 프로세스 종료 코드는 0이고, 결과 파일·모든 단계 로그·진행 기록에서 기준 HEAD 일치와 clean 상태를 확인했다. 이후 이력 문서와 목차만 추가하며 코드가 같으므로 전체 검사를 반복하지 않는다.

```text

```

| 검사 | 결과 |
