# 마이 통계 조회 상태·복구 구현 티켓 분할

## 기준과 승인

- 원문은 [구현 스펙 #80](https://github.com/clip-back/clipback/issues/80)입니다. 작성 기준 코드는 `f31c6c9`이며, [정책](../frontend/account-stats-recovery.md)과 [원문 사본](../frontend/account-stats-recovery-spec.md)을 대조했습니다.
- 요청한 `to-tickets` 스킬에 따라 원문의 전체 본문·댓글·기존 하위 이슈를 조회했습니다. 조회 당시 원문은 로컬 사본과 일치했고 댓글·하위 이슈는 없었습니다.
- 사용자는 연결된 초안 본문 그대로 4개 하위 이슈를 생성하고 `ready-for-agent` 라벨·GitHub 기본 선행 관계를 연결하는 안을 승인했습니다.
- 화면·조회·통합 테스트를 함께 완성하는 동작 단위로 나눴습니다. 별도 계층별 작업이나 대규모 선행 리팩터링 티켓은 만들지 않았습니다.

선행 관계는 실제 GitHub 관계로 설정했습니다. #82와 #83 사이에는 직접 선행 관계를 두지 않았습니다.
작업 가능 여부는 GitHub에서 선행 이슈의 종료 여부로 판단합니다. 위 표는 승인된 관계이며 현재 진행 상태를 복제한 목록이 아닙니다.
기본 인증·계정 보호는 초기 티켓부터 유지하고 #84에서 새 경로들이 함께 사용하는 복합 경계를 완성하도록 했습니다.

## 검증 결과

- 원문의 사용자 스토리 36개를 4개 티켓에 배정해 누락이 없는 것을 확인했습니다.
- 각 티켓의 부모 참조·사용자 동작·수용 기준, 구체 파일 경로 제외, 의존 관계의 선행 순서·순환 부재를 확인했습니다.
- 모든 티켓에 기존 실제 앱·HTTP 대역 통합 테스트와 iOS Simulator·Android Emulator 실행 및 화면 증거를 수용 기준으로 포함했습니다. 작업별 상세 수용 기준은 각 GitHub 이슈에서 관리합니다.
- 생성 후 4개 이슈를 다시 조회해 승인한 초안과의 본문 일치, 제목, `ready-for-agent` 라벨, 부모 #80, 정확한 선행 관계와 열린 상태를 확인했습니다. 본문 비교에서는 개행 형식과 마지막 개행만 정규화했습니다.
- 부모 #80의 본문·제목·상태·라벨은 생성 전과 같았습니다. 하위 관계만 추가했고 부모 본문 수정·종료·댓글 추가는 하지 않았습니다.
- 첫 검증 보조 스크립트는 연결형 JSON을 목록으로 해석해 실패했습니다. 실제 `nodes`·`totalCount` 구조를 확인해 수정한 뒤 같은 범위를 재조회하여 통과했습니다. 이 과정에서 원격 이슈를 다시 만들거나 수정하지 않았습니다.
- 로컬 문서 링크·앵커와 공백을 검사했습니다. 제품 코드 변경이 없는 티켓 분할 작업이므로 앱 테스트·빌드·네이티브 실행은 수행하지 않았습니다.

## 범위

이번 작업은 승인된 하위 이슈와 선행 관계의 생성입니다. 제품 구현·푸시·PR 생성·배포는 수행하지 않았습니다.
