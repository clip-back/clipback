### 14. 2026-09-24 Today 선정·일별 조회

<a id="b-df33f28517704543"></a>

- 인증된 Today GET API를 추가했다. 현재 콘텐츠 수 기반 Stage, KST 날짜, 배치 정보, 최초 항목 ID·순위와 최신 콘텐츠 정보를 반환하며 응답 캐시를 금지한다. 조회·선정은 열람·노출·카운터를 갱신하지 않는다.
- Stage 1은 전날 실제 노출과 열람·저장 우선순위로 선정한다. Stage 2는 시간 제외·노출/저장 제한 완화·합의 점수와 상위 후보군·카테고리 상한을 적용해 중복 없이 가중 추첨하고 그 순서를 저장한다.
- 당일 최초 비어 있지 않은 결과를 고정한다. 이후 열람·즐겨찾기·분류·Stage 변경에도 다시 선정하지 않고 삭제된 항목만 제외한다. 전체 삭제 후에도 배치는 유지하며 Stage 0으로 감소했다 복귀하면 같은 배치를 재사용한다.
- 사용자 잠금과 최초 선정의 콘텐츠 SHARE 잠금으로 중복 배치·삭제 경쟁을 처리한다. 잠금 이후 Stage·KST 날짜를 재확인하며, 기존 배치 조회는 전체 콘텐츠를 잠그지 않는다. 실패 시 배치·항목을 함께 롤백한다.
- 순수 알고리즘 51개·API 통합 23개·독립 연결 동시성 14개를 추가했다. Python 3.12.7 및 격리 PostgreSQL 17.7에서 전체 **717개 테스트 통과**(88개 추가, DB 테스트 생략 없음). 빈 DB upgrade·모델 일치, Ruff·compileall·Git diff 검사를 통과했다. 기존 Starlette/httpx 경고 1건은 남아 있다.
- 신규 마이그레이션·노출 수집·Weekly·프론트 변경은 없다. 추천 계획은 3단계까지 완료이며 4~7단계는 미착수다. 노출 관련 선정은 fixture로 검증했고 원격 CI·Docker·운영 배포·실기기는 미검증이다.

### 2026-09-24 3단계 구현·검증

<a id="b-c2a232862c945ddf"></a>

- 인증된 `GET /api/v1/recommendations/today`를 추가했다. 성공 시 200·`Cache-Control: no-store`, 현재 Stage·KST 날짜·배치 정보·원래 순위와 항목 ID·최신 `ContentRead`를 반환한다. 점수는 DB에만 저장한다.
- Stage 1은 실제 전날 콘텐츠 노출을 조회해 미노출·미열람·오래된 열람·최근 저장 순으로 선정한다. Stage 2는 합의한 시간 필터·순차 완화·5요소 점수·상위 후보군·가중 비복원 추첨·복수 분류 상한을 적용하고 추첨 순서를 유지한다.
- 첫 비어 있지 않은 배치만 저장한다. 최초 후보 0개는 다음 요청에서 재평가하고, 저장된 결과는 삭제·열람·즐겨찾기·분류·Stage 변경으로 다시 선정하지 않는다. 삭제된 항목은 보충·재번호 부여하지 않으며 Stage 0도 기존 배치 정보는 보존한다.
- 사용자 `FOR NO KEY UPDATE`와 신규 선정 콘텐츠의 ID순 `FOR SHARE` 잠금으로 배치·항목을 원자적으로 저장한다. 콘텐츠 잠금 이후 Stage와 기준 시각을 확정하고 KST 자정 통과 시 새 날짜 배치를 확인한다. 기존 배치 조회는 전체 콘텐츠를 잠그지 않는다.
- 순수 알고리즘 테스트 51개, PostgreSQL API 통합 23개, 독립 연결 동시성 14개를 추가했다. 경계·추첨·당일 유지·사용자 격리·최신 카드·조회 무집계·추천 항목 view 연결, 생성/응답/커밋 실패 롤백과 대기 요청 복구를 검증했다.
- 동시성은 실제 DB 잠금 대기를 확인했다. 같은 사용자 배치 하나·다른 사용자 독립 처리, 삭제·열람·분류 변경의 양쪽 잠금 순서, 자정 통과, 선정 이후 신규 저장의 다음 요청 Stage 반영을 검증했다.
- Python 3.12.7 및 격리 PostgreSQL 17.7에서 전체 **717개 테스트 통과**(88개 추가, DB 테스트 생략 없음). 빈 DB `alembic upgrade head`, `alembic check`, Ruff, compileall, Git diff 검사를 통과했다. 기존 Starlette/httpx 경고 1건은 남아 있다.
- 신규 마이그레이션·노출 수집·Weekly·프론트 변경은 없다. 노출 기반 선정은 fixture로 검증했으며 실제 노출 수집은 4단계에 구현한다. 원격 CI·Docker·운영 배포·실기기 검증은 실행하지 않았다.
