## 문제와 결정

- 자동 요약이 명사형 조각을 이은 한 문단이라 무엇을 다루는지 한눈에 보기 어려웠다.
- 결정([ADR 0005](../adr/0005-summary-headline-and-points-as-plain-text.md), [용어집](../../GLOSSARY.md)의 핵심 한 줄·요점):
  모델에게서 핵심 한 줄과 요점 1–5개를 따로 받고, 서버가 공통 정리 규칙으로 다듬어 `핵심 한 줄\n• 요점…` 평문 하나로 저장한다.
  `/api/v1` 응답·DB 구조는 그대로라 앱 업데이트가 필요 없고, 이미 저장된 요약은 바뀌지 않는다.
- 정리 순서·기호 떼기·공백 합치기·500자 판정은 #203 "공통 정리 규칙과 결과 판정"의 표를 따른다(2026-11-03 사용자 결정 A·B·R1·R2·R3 포함).
- 구현 중 사용자 결정(2026-11-03)
  - 판정 표의 "공백 합치기를 기호 떼기 뒤로" 순서 변형은 모든 입력에서 결과가 같아 테스트로 실패시킬 수 없다. 근거를 남기고 완료 조건 충족으로 봤다.
  - #205 촬영 상태 `archive-card`의 "보관함 카드 13줄"은 앱에서 쓰이지 않는 카드(`CategoryFeaturedCard`)였다. 랜덤 카드 보기의 첫 카드로 바꿨다(#205 본문 반영).
- 이슈 본문에 없던 해석(구현 판단, 사용자 미확정): 공백 합치기와 "기호 바로 뒤가 공백" 조건은 일반 공백(U+0020)만 보고, 기호의 숫자는 ASCII 숫자만 본다.
  그래서 `a\t\tb`·`-\t내용`·`２. 내용`은 그대로 남는다. 앞뒤 공백 제거는 탭·Unicode 공백도 지운다.

## 변경 내용

- `backend/app/integrations/summary.py`: 공통 판정 `validated_result`가 제목·핵심 한 줄·요점·카테고리를 받아 내부 `_joined_summary`로 정리·합친 뒤
  제목 120자·합친 요약 500자·카테고리를 판정한다. 옛 요약 문자열 검증 경로는 없앴다.
- `backend/app/integrations/youtube_summary_client.py`: Gemini 응답 스키마를 `title`·`headline`(maxLength 40)·`points`(1–5개, 항목 maxLength 60)·`category_id`로 바꾸고
  지시문을 새 형식으로 바꿨다. 응답 키 집합이 정확히 같아야 하며, 추가 키·옛 `summary` 키는 `invalid_response`다.
- `backend/app/integrations/instagram_summary_client.py`: OpenAI `text.format` 스키마를 같은 구조로 바꿨다. 개수·길이 제한은 요청 스키마에만 넣고
  SDK 파싱에서는 거절하지 않는다. 스키마 밖 추가 키는 지금처럼 무시한다. "제공된 캡션과 이미지 1장만 근거" 등 [ADR 0002](../adr/0002-instagram-summary-caption-and-image.md) 문구는 그대로다.
- 오류 코드·재시도·로그 항목·`/api/v1` 응답·DB 스키마·앱 코드(`frontend/lib`)는 바뀌지 않았다.
- 문서: [유튜브 요약](../youtube-summary.md)의 형식·출력 키·정리 순서와 인스타그램 절, `CHANGELOG.md` `미배포` > 개선,
  [Figma 화면 맞춤 계획](../figma-ui-alignment-plan.md) '디자인 확인 필요'의 요약 목록 모양 항목(요점 내어쓰기·간격, 카드 표시 범위).

## 시뮬레이터·에뮬레이터 실행 (#205, 2026-11-03)

- 환경: iPhone 16 / iOS 18.6 Simulator(393×852pt), Android Emulator `Medium_Phone` / Android 16(1080×2400, 411.4×914.3dp). 한 번에 하나만 띄웠고 서버·로그인은 쓰지 않았다.
- 앱 코드가 바뀌지 않아 같은 코드에서 요약 데이터만 바꾼 임시 진입 파일(커밋하지 않음)로 세 가지를 debug 빌드했다.
  `old`는 옛 모양(지어낸 182자 한 문단), `one`·`five`는 요점 1개·5개인 새 모양이며 백엔드 `validated_result`로 합친 글자와 같다. 콘텐츠는 1개만 둔다.
- 상태 4개 × 데이터 3개 × 2플랫폼 24장을 찍었다. 이동은 Orca 에뮬레이터의 화면 구조(`ax`)에서 글자를 찾아 탭했고, 찍기 전 진입 파일의 상태 판정이 찍을 상태와 같은지 확인했다.
  글자 배율 1.0, 스크롤 0, 대역 API의 예상 밖 요청 없음으로 세 데이터의 조건이 같다.

  | 상태 | 결과(두 플랫폼 같음) |
  | --- | --- |
  | 상세 요약 | 핵심 한 줄과 요점이 줄마다 보인다. `five`의 두 번째 요점은 두 줄로 넘어가고 다음 줄이 `•` 아래가 아니라 줄 맨 앞에서 시작한다 |
  | 홈 최근 카드(3줄) | 핵심 한 줄과 첫 요점이 보이고 `five`는 두 번째 요점에서 말줄임 |
  | 아카이브 전체보기 목록 카드(2줄) | 핵심 한 줄과 첫 요점까지 |
  | 랜덤 카드 보기 | `five`의 요점 5개가 모두 보인다 |

- Orca 에뮬레이터: 두 플랫폼에서 상세 요약 문구(핵심 한 줄 + 요점 5줄)를 화면 구조에서 확인했다. iOS는 스와이프로 상세가 끝(89pt)까지 스크롤됐고,
  Android는 화면이 길어 스크롤할 거리가 없었다(뒤로 가기 버튼으로 홈 복귀 확인).
- Figma 기준 화면은 요약 목록 모양의 디자인이 없어 비교에서 빠졌다. 측정 JSON의 `viewPadding`이 0인 것은 `SafeArea` 아래 위젯에서 읽은 값이라서이며
  실제 OS 안전 영역 값이 아니다. 원본 화면은 보정하지 않았다.
- 사용자 판정(2026-11-03): 통과.

## 미검증과 범위 밖

- 운영 서버 배포 뒤 실제 링크 저장으로 새 요약이 저장되는지, 배포된 앱(TestFlight·Play 내부 테스트)과 실기기 화면은 확인하지 않았다(범위 밖, 배포 뒤 사람이 확인).
- Docker가 필요한 deployment 테스트는 로컬에서 건너뛰었다. 이번 변경 범위가 아니다.
- 요점 목록의 내어쓰기·간격과 카드 표시 범위는 디자인 확인 뒤 별도로 구현한다('디자인 확인 필요').
