## Problem Statement

허투루 운영자는 승인된 개인 Google Play 개발자 계정과 `com.huturu.app` 앱을 가지고 있지만,
본인의 Android 기기에 Play를 통해 설치하여 실제 서비스 동작을 확인할 수 있는 내부 테스트 버전이 없다.
Android Release 설정은 Debug 키를 사용하며, Android 배포 후보와 업로드 가능한 Release AAB도 아직 없다.
패키지명 변경과 로컬 테스트 통과만으로는 Play가 서명한 설치본의 소셜 로그인·공유·저장이 동작하는지 알 수 없다.

디스크 부족으로 모바일 실행 검증이 중단된 이력도 있다. 업로드, Play의 처리 완료,
테스터 제공, 실제 설치·실행을 하나의 배포 성공으로 취급하면 미검증 상태를 놓치게 된다.
이번 목표는 Android 내부 테스트를 본인 1명에게 제공하고 실제 기기에서 핵심 기능을 검증하는 것이다.
비공개 테스트와 정식 출시는 이후 단계다.

## Solution

Android 사용자 버전 `0.2.0`, 빌드 번호 `1`을 첫 후보로 준비한다. 예약 직전 업로드 이력과 기존 예약을
다시 확인하며, 사용할 수 없는 번호라면 기존 기록을 덮어쓰지 않고 충돌을 보고한다.
운영 서버에 별도 테스트 계정·콘텐츠를 사용하고, Google이 생성한 앱 서명 키를 사용하는
Play App Signing과 별도의 업로드 키를 구성한다. 업로드 키와 비밀번호는 저장소 밖에 보관하고
파일 첨부가 가능한 암호관리자에 백업하여 복구를 확인한다.

고정한 소스에서 Release AAB를 만들고, 실제 Play 앱 서명 인증서에 맞춰 Google·카카오 로그인을
설정한다. 본인 Google 계정을 첫 내부 테스터로 등록하여 참여 링크를 통해 Play에서 설치한다.
Android 실기기에서 로그인, 로그아웃·재로그인, 링크·사진 저장, 시스템 공유 저장,
앱 재시작 후 같은 계정의 데이터 확인이 모두 성공해야 내부 테스트 완료로 판단한다.

## User Stories

1. 앱 운영자로서, iOS와 같은 `com.huturu.app`으로 Android 앱을 식별하여 두 플랫폼의 서비스 등록을 일관되게 관리하고 싶다.
2. 앱 운영자로서, 실제 빌드한 소스 커밋을 고정하여 문제가 발생했을 때 어느 코드가 배포되었는지 확인하고 싶다.
3. 앱 운영자로서, 첫 Android 후보를 `0.2.0(1)`로 준비하여 사용자 버전은 iOS와 맞추고 빌드 번호는 플랫폼별로 관리하고 싶다.
4. 앱 운영자로서, 후보 예약 전에 Play 업로드 이력과 기존 예약을 확인하여 이미 사용한 번호를 재사용하지 않고 싶다.
5. 앱 운영자로서, Release 빌드를 업로드 키로 서명하여 Debug 서명 때문에 업로드가 거절되는 일을 피하고 싶다.
6. 앱 운영자로서, Google이 앱 서명 키를 관리하게 하여 실제 사용자 설치본의 서명과 업데이트 경로를 안정적으로 유지하고 싶다.
7. 앱 운영자로서, 업로드 키와 앱 서명 키의 역할을 구분하여 소셜 로그인에 잘못된 인증서를 등록하지 않고 싶다.
8. 앱 운영자로서, 업로드 키와 비밀번호를 암호관리자에 백업하고 복구를 확인하여 개발 Mac을 사용할 수 없어도 다음 빌드를 준비하고 싶다.
9. 앱 운영자로서, 키·비밀번호·토큰이 Git, 채팅, 실행 로그에 남지 않게 하여 배포 자격 증명의 노출을 막고 싶다.
10. 앱 운영자로서, 서명 설정이 빠졌을 때 Release 빌드가 명확하게 실패하게 하여 잘못된 산출물을 정상 후보로 취급하지 않고 싶다.
11. 앱 운영자로서, 제품 진입점과 운영 API 설정으로 Release AAB를 만들어 테스트 프리뷰를 잘못 배포하지 않고 싶다.
12. 앱 운영자로서, 완성한 AAB의 패키지·버전·서명·권한·기기 호환성을 확인하여 소스 설정과 산출물의 차이를 업로드 전에 발견하고 싶다.
13. 앱 운영자로서, 디스크 부족 등 환경 문제를 먼저 해결하여 불완전한 빌드 결과를 배포에 사용하지 않고 싶다.
14. 내부 테스터로서, 본인 Google 계정으로 참여 링크를 열어 Play에서 설치하여 일반 사용자가 받을 경로와 같은 방식으로 확인하고 싶다.
15. 앱 운영자로서, 본인 1명에게 먼저 테스트를 제공하여 문제를 파악한 뒤 팀·지인에게 범위를 넓히고 싶다.
16. 내부 테스터로서, Play 설치본에서 Google 로그인을 완료하여 올바른 서비스 계정으로 기능을 사용하고 싶다.
17. 내부 테스터로서, Play 설치본에서 카카오 로그인을 완료하여 해당 계정의 서비스 데이터를 확인하고 싶다.
18. 내부 테스터로서, 별도의 테스트 계정과 콘텐츠를 사용하여 운영 경로를 검증하면서 다른 사용자의 데이터를 건드리지 않고 싶다.
19. 내부 테스터로서, 링크를 저장하고 다시 열어 실제 서버에 저장된 콘텐츠를 확인하고 싶다.
20. 내부 테스터로서, 사진을 저장하고 원본 이미지를 다시 열어 서버 보관과 재열람이 동작하는지 확인하고 싶다.
21. 내부 테스터로서, 다른 앱의 Android 공유 메뉴에서 링크를 허투루에 저장하여 앱 간 공유 경로를 확인하고 싶다.
22. 내부 테스터로서, 다른 앱에서 공유한 이미지 URI를 허투루에서 저장하여 실제 공유 권한과 원본 이미지 저장을 확인하고 싶다.
23. 내부 테스터로서, 로그아웃 후 같은 제공자로 재로그인하여 기존 계정의 콘텐츠를 계속 볼 수 있는지 확인하고 싶다.
24. 내부 테스터로서, 앱을 종료하고 다시 실행해 같은 계정의 저장 결과를 확인하여 일시적인 화면 표시를 저장 성공으로 오해하지 않고 싶다.
25. 내부 테스터로서, 발견한 문제를 정해진 피드백 경로로 전달하여 다음 내부 테스트 빌드에 반영하고 싶다.
26. 앱 운영자로서, 업로드·처리·테스터 제공·설치·핵심 기능 검증 상태를 따로 기록하여 어느 단계가 완료되었는지 판단하고 싶다.
27. 앱 운영자로서, 수정 후 새 빌드를 준비할 때 기존 후보와 검증 기록을 보존하여 버전 추적을 이어가고 싶다.
28. 앱 운영자로서, iOS 0.2.0 빌드 6과 기존 릴리스 산출물을 보존하여 Android 준비가 이미 진행한 iOS 배포를 바꾸지 않게 하고 싶다.
29. 앱 운영자로서, 실행할 수 없는 검증의 이유와 미검증 범위를 확인하여 자동 테스트 통과를 실기기 성공으로 잘못 보고하지 않고 싶다.
30. 앱 운영자로서, 내부 테스트 완료와 비공개 테스트·정식 출시의 남은 조건을 구분하여 다음 단계의 준비를 빠뜨리지 않고 싶다.

## Implementation Decisions

- **범위와 대상**: 기존 허투루 Google Play 앱의 내부 테스트 트랙을 사용한다. 앱의 무료 설정과
  `com.huturu.app`을 유지한다. 내부 Java namespace나 기존 공유 채널 계약을 바꾸는 작업은 필요하지 않다.
- **버전과 소스**: 첫 목표는 `0.2.0(1)`이다. 기존 배포 후보 도구와 기록 형식을 재사용해 Android만
  준비하며, 패키지명·Release 서명 변경이 포함된 검증 대상 소스를 고정한다. 예약 직전 Play 이력,
  기존 후보·태그를 확인하고 확인 시점·최대 업로드 번호·소스를 남긴다. 이력이 미확인이거나 충돌하면
  배포 준비 완료로 표시하지 않는다. 재빌드로 소스나 설정이 달라지면 기존 번호·후보를 덮어쓰지 않는다.
- **Release 서명**: Android 빌드 설정에 별도의 업로드 키를 사용하는 Release 서명을 연결한다.
  키·별칭·비밀번호 등 필요한 입력이 없거나 잘못되면 배포용 빌드는 실패해야 하며 Debug 키로 대체하지 않는다.
  일반 Debug 개발·테스트는 Release 비밀값 없이 기존 방식으로 가능해야 한다.
- **키 책임과 복구**: 앱 서명 키는 Google이 생성·관리하고 업로드 키는 운영자가 관리한다.
  키 파일은 저장소 밖에 두며 비밀번호와 함께 파일 첨부 가능한 암호관리자에 백업한다.
  백업에서 복원한 키로 서명할 수 있고 업로드 인증서가 일치하는지 확인한다.
  코드·문서에는 설정 방법만 남기며 실제 비밀값·인증 토큰·개인 계정 정보는 남기지 않는다.
- **산출물**: 충분한 디스크 여유를 확보한 뒤 정상적인 Release 빌드 절차로 AAB를 만든다.
  제품 앱 진입점, 운영 API, 필요한 소셜 공개 설정을 사용한다. 프리뷰 진입점·HTTP 대역·Debug APK는
  배포 후보가 아니다. 완료된 산출물의 해시, 소스, 버전·빌드, SDK·도구 버전과 검증 결과를 연결한다.
  이전 디스크 부족 실행의 부분 산출물이나 빌드 단계 우회를 Release 검증으로 대신하지 않는다.
- **플랫폼 적합성**: 최종 AAB의 패키지·버전·서명·실제 권한·target SDK와 포함된 네이티브 라이브러리의
  16KB 페이지 호환을 확인한다. 출시 시점의 Play 요구사항과 대조하며 Debug 산출물의 확인값을 복사하지 않는다.
- **Play App Signing과 소셜 등록**: 첫 업로드 과정에서 Google 생성 키를 선택하고 앱 서명 인증서를
  확인한다. Google에는 패키지와 실제 설치본의 SHA-1, 카카오에는 패키지와 해당 인증서의 key hash를
  등록한다. 로컬 빌드용 인증서와 Play 설치본 인증서를 구분하고 기존 iOS·정상 제공자 설정을 보존한다.
  Google 앱 서명 비밀키를 내려받아 로컬에서 사용하는 방식을 전제로 하지 않는다.
- **서버와 계정**: 기존 운영 서버와 이미 제공되는 인증·저장·공유 API를 사용한다.
  별도 테스트 계정·테스트 콘텐츠를 사용하며 운영 데이터가 실제 생성됨을 기록한다.
  기존 계정 간 데이터 격리와 원본 이미지 보관 계약을 유지한다. 테스트용 인증 우회, 서버 인증 완화,
  새 데이터베이스 스키마 또는 새로운 API는 이번 배포 준비를 위해 추가하지 않는다.
- **내부 제공 순서**: 검증된 AAB를 내부 테스트 트랙에 업로드하고 처리·검증 상태를 확인한다.
  본인 Google 계정을 첫 테스터로 지정하고 피드백 경로를 설정한다. 참여 링크에서 테스트 참여를
  완료한 뒤 Play로 설치한다. 목록 등록, 참여 완료, 설치 성공은 각각 확인한다.
  팀·지인 추가는 본인 검증 후 후속으로 진행하며 자동 초대·메시지 발송은 하지 않는다.
- **검증과 상태 기록**: 준비, 업로드, Play 처리, 테스터 제공, 실기기 설치, 실제 OAuth·핵심 기능 결과를
  기존 배포 기록에서 구분한다. 단계별 시간, 대상 빌드, 기기·OS, 결과와 재확인 가능한 증거를 남긴다.
  실패·미확인 상태를 성공으로 승격하지 않는다. 업로드 응답이 불명확하면 Play 상태를 확인한 뒤 재시도를 판단한다.
- **운영 입력과 실행 경계**: 사용할 암호관리자·보관 위치, 테스터 Google 계정, Android 기기,
  피드백 연락처는 해당 실행 단계 전에 제공받는다. 사용자가 직접 입력해야 하는 비밀번호·인증 코드는
  채팅으로 받지 않는다. 개인 파일 정리·이동·삭제는 별도 승인 없이 진행하지 않는다.
  명세 발행은 키 생성, 공급자 설정 변경, Play 업로드·출시, 초대 실행을 이미 수행했다는 뜻이 아니다.

## Testing Decisions

**주 검증 경계는 Play 설치본을 사용하는 본인 Android 실기기의 전체 사용자 흐름**이다.
이는 설계 인터뷰에서 사용자가 동의한 완료 기준이다. 내부 구현의 필드·함수 호출 횟수 대신
설치 가능한 앱, 인증 결과, 저장된 데이터, 공유 결과와 재진입 후 상태를 관찰한다.
자동 검사는 이 경계에 도달하기 위한 보조 증거이며 실제 제공자·운영 서버·실기기 증거를 대체하지 않는다.

- **배포 후보**: 기존 CLI 통합 테스트 경계를 재사용한다. 실제 명령의 입력·종료 결과와 생성 기록을
  확인하며 Android 단독 후보, 플랫폼별 소스·빌드 분리, 스토어 이력 미확인, 번호 충돌,
  재실행 시 기존 기록 보존의 기존 사례를 따른다. 도구를 변경하지 않으면 같은 로직의 중복 테스트를 추가하지 않는다.
- **서명과 AAB**: 실제 Release 빌드 명령과 생성 산출물을 검사한다. 올바른 입력으로 업로드 키 서명 AAB가
  만들어지고, 필수 서명 입력 누락·잘못된 키/비밀번호는 성공 산출물로 보고되지 않아야 한다.
  Debug 빌드는 Release 비밀값 없이 가능해야 한다. 오류 로그에 비밀번호·키 내용이 노출되지 않는지 확인한다.
  설정 파일의 문자열 모양만 비교하는 테스트로 서명 성공을 주장하지 않는다.
- **앱 회귀**: 기존 Flutter 분석·전체 테스트와 소셜 인증·세션 복원·저장·공유 생명주기 테스트를 활용한다.
  Android 네이티브 공유 저장소·Activity·HTTP fixture 테스트는 기존 로컬 대역 경계에서 실행한다.
  대역 테스트 중 운영 API로 우회하지 않으며, 결과는 운영 경로 검증과 분리한다.
- **모바일 실행**: 프론트엔드 변경은 저장소 기준에 따라 Android Emulator와 iOS Simulator에서 실행 확인한다.
  이번 완료 판정에는 추가로 Play에서 설치한 Android 실기기가 필요하다. 실제 기기 모델·OS·설치 빌드를
  기록하고 앱 시작·로그인·저장 결과의 스크린샷, 시스템 공유·복귀 흐름의 영상을 남긴다.
  사용자 데이터·토큰이 보이는 증거는 공개 저장소에 올리지 않는다. 화면 디자인 변경이 생기면 기존 디자인 확인·비교 규칙을 따른다.
- **실제 사용자 흐름**: Google·카카오 로그인을 각각 실제 제공자로 완료한다. 테스트 계정으로 링크와 사진을
  앱에서 저장하고 다시 열며, 다른 앱의 시스템 공유 메뉴로 링크와 이미지도 저장한다.
  로그아웃 후 같은 제공자로 재로그인하고 앱을 종료·재실행했을 때 같은 계정의 결과가 보여야 한다.
  Google·카카오 계정을 합치는 새로운 동작은 요구하지 않는다.
- **복구·환경**: 백업에서 복원한 업로드 키의 인증서·서명 가능 여부를 확인한다.
  공간 부족, 콘솔 접근, 키 입력, 기기 준비 또는 실제 제공자 설정이 막히면 해당 단계와 이유를 기록한다.
  이전 실행의 통과 수치를 새 검증으로 사용하거나 미실행 항목을 통과로 집계하지 않는다.

## Further Notes

- 2026-10-28 KST 설계 인터뷰의 7개 결정에 기반한다. 당시 Play Console에서 개인 계정,
  무료 허투루 앱, 내부 테스트 비활성, 출시·최신 App Bundle 없음, 비공개 테스터 0명을 확인했다.
  이는 조회 당시의 상태이며 후보 예약·업로드 전에 다시 확인한다.
- Android 식별자 변경과 설계 기록은 로컬 커밋에 보존되어 있다. 구현 시작 시 최신 기준 소스에 필요한
  변경이 포함되어 있는지 확인한다. 명세는 새로 버전 번호를 예약하거나 코드를 배포한 기록이 아니다.
- 운영 입력이 아직 정해지지 않은 항목은 실행에 필요한 값이며 설계 방향을 다시 인터뷰할 이유가 아니다.
  입력이 없는 상태에서도 독립적인 코드·문서·자동 검증 작업은 진행할 수 있으나 해당 운영 단계는 완료로 보고하지 않는다.
- 내부 테스트만 제공하는 앱의 데이터 보안 양식 예외와, 앱의 실제 개인정보·계정 삭제 책임을 구분한다.
  회원 탈퇴 미구현과 운영 정책 미확정은 비공개 테스트·정식 출시 전 해결할 후속 작업으로 추적한다.
- 이 앱의 정식 출시에는 최소 12명이 14일 연속 참여하는 비공개 테스트와 프로덕션 액세스 신청이 필요하다.
  내부 테스트 기간은 그 기간에 합산하지 않는다. 내부 테스터가 비공개 테스트에 참여할 때에는
  내부 테스트에서 탈퇴한 뒤 비공개 테스트 참여를 완료한다. 요건 충족이 자동 승인·공개를 뜻하지 않는다.
- GitHub 이슈에 게시된 본문을 실행 명세의 기준으로 삼고 로컬 사본과 일치시킨다.
