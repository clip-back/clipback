# 콘텐츠 재발견 추천 정책과 구현 현황

현재 합의 정책과 코드 위치를 정리합니다. 이관 기준 커밋에서 백엔드 1~5단계와 Today·Weekly 프론트 연결이 구현되어 있습니다.
상세 검증 결과와 과거 계획은 [작업 이력](history/README.md)에 보존합니다. 아래 구현 상태는 신규 실행 검증이나 운영 품질 확인을 뜻하지 않습니다.

## 1. 목적과 범위

사용자가 이미 저장한 콘텐츠를 다시 발견할 수 있도록 오늘의 콘텐츠(Today)와
이번 주 허투루 픽(Weekly Pick)을 구현한다. 추천 선정, 실제 화면 노출, 상세 열람을
서로 다른 사건으로 관리한다.

2026-09-23 작성된 「추천 알고리즘 백엔드 개발 전달사항」과 이후 합의한 정책을 바탕으로 한다.
원문과 다른 동작은 아래 합의 정책을 따른다. 주요 변경은 Stage 1 후보 부족 시 전날 추천 재허용,
당일 삭제·Stage 변경 처리, 복수 카테고리 지원, Weekly 동일 카테고리 카드 중복 방지다.

기존 복수 카테고리, 영구 삭제, 별도 상세 열람 POST, 이벤트 기반 마이페이지 누적 통계를 유지한다.
자동 분류용 `CategoryRecommendationService`와 이번 재발견 추천은 별도 기능이다.
PUSH 발송, CATEGORY_RANDOM 전용 기능, 관리자 설정 화면, ML 모델, 콘텐츠 상태 체계 신설은 범위에 포함하지 않는다.

2~7절은 합의한 제품 동작이다. 8절의 DB 구조는 1단계, 저장·열람 수집과 view POST 확장은
2단계에서 구현했다. Today 선정·일별 조회는 3단계, 콘텐츠·카테고리 노출 수집은 4단계에서
구현했다. Weekly 집계·선정·조회는 5단계에서 구현했다. 프론트의 Today 버튼·상세 탐색과 Weekly 표시·카테고리 이동·실제 카드 노출·추천 유입은 각 작업 기록의 승인 범위로 연결되어 있다. 운영 추천 품질·실기기 검증은 별도다.

## 2. 추천 대상과 시간 기준

### 정상 콘텐츠와 Stage

정상 콘텐츠는 현재 사용자가 보유하고 있으며 저장이 완료되어 상세 열람 가능한 콘텐츠다.
YouTube 요약이 대기·처리 중이거나 실패·제외되어도 링크를 이용할 수 있으면 포함한다.
요약 작업 상태를 콘텐츠 정상 여부에 직접 대응시키지 않는다.
현재 상세 API와 동일하게 본인 소유 `contents` 행 전체를 사용하며, 외부 URL·파일 존재 검사를 추가하지 않는다.

Stage는 현재 정상 콘텐츠 행 수로 판단한다. 누적 저장 이벤트 수나 카테고리별 개수의 합계를 사용하지 않는다.

| Stage | 정상 콘텐츠 수 | Today 동작 |
| --- | --- | --- |
| 0 | 0~4개 | 미노출 |
| 1 | 5~9개 | 우선순위 기반 최대 5개 |
| 2 | 10개 이상 | Today Score와 가중 랜덤 기반 최대 5개 |

Weekly Pick은 Today Stage와 독립적이다. 유효한 카테고리가 있으면 최대 2개 카드를 제공한다.

### 시간

| 항목 | 기준 |
| --- | --- |
| DB 시각 저장 | UTC, 시간대가 있는 timestamp |
| Today 날짜·전날 | `Asia/Seoul` 달력 날짜, 자정에 변경 |
| Weekly 기간 | 한국 시간 오늘을 포함한 7개 날짜의 첫날 00시부터 현재 시각까지 |
| 최근 열람 제외 | 실제 경과 24시간 미만 |
| 최근 저장 제외 | 실제 경과 48시간 미만 |
| 최근 추천 제외 | 실제 경과 72시간 미만 |
| 점수의 경과 일수 | 실제 경과 초 / 86,400, 소수점 유지 |

예를 들어 9월 23일 15시의 Weekly 기간은 9월 17일 00시부터 9월 23일 15시까지다.
직전 168시간이나 월요일 시작 주간으로 해석하지 않는다.
경과 시간이 정확히 24·48·72시간에 도달하면 해당 제외 조건에서 벗어난다.

## 3. 저장·열람·노출 이벤트

### 저장과 상세 열람

- 저장 시 실제 배정된 모든 카테고리를 저장 이벤트에 스냅샷으로 기록한다.
- 상세에 실제 진입하면 열람 이벤트, 당시 모든 소속 카테고리, 마지막 열람 시각, 열람 횟수를 기록한다.
- 본 저장·열람 이벤트는 행동당 1행이다. 복수 카테고리 때문에 본 이벤트를 여러 개 만들지 않는다.
- 상세 GET, 요약 상태 폴링, 카드 노출, 화면 재렌더링은 열람으로 기록하지 않는다.
- 새 상세 진입마다 새 이벤트 ID를 발급하고, 통신 재시도에는 같은 ID를 사용한다.
- 같은 이벤트의 재전송은 횟수·시각·스냅샷을 다시 갱신하지 않는다.
- 실제 반복 진입은 각각 열람으로 센다. 마이페이지는 이 이벤트 기준 누적 횟수를 유지한다.
- 추천에서 진입했으면 추천 위치·추천 결과 식별정보를 연결해 일반 열람과 구분한다.

직접 링크·공유·스크린샷 저장은 공통 `ContentService.create_content()`에서 처리한다.
카테고리 자동 추천 결과의 ID가 아닌 최종 실제 소속 카테고리를 기록해야 한다.
YouTube 비동기 분류 완료, 사용자 분류 변경, 카테고리 삭제에 따른 이동은 과거 스냅샷을 바꾸지 않는다.
자동 분류 완료를 새로운 저장 행동으로 세지 않는다.

### 실제 추천 노출

- 추천 결과 생성이나 API 응답만으로는 노출을 기록하지 않는다.
- 프론트에서 카드가 실제 화면에 표시될 때 대상별 노출 이벤트를 전송한다.
- 같은 홈 방문에서 재렌더링·통신 재시도는 중복 집계하지 않는다.
- 다른 홈 방문에서 다시 보이면 새로운 노출이다. 하루 3회 방문에서 보이면 3회로 센다.
- 노출마다 이벤트 ID를 발급하고 같은 노출의 재전송에는 같은 ID를 사용한다.
- 콘텐츠 노출은 해당 콘텐츠의 마지막 추천 시각·추천 횟수·마지막 추천 위치를 갱신한다.
- 카테고리 카드 노출은 별도로 기록한다. 소속 콘텐츠 전체를 노출된 것으로 처리하지 않는다.
- 어느 노출도 `open_count`와 `last_viewed_at`을 변경하지 않는다.

따라서 `recommendation_count`는 일별 고유 추천 횟수가 아니라 중복 전송을 제거한 실제 노출 횟수다.
노출 기록과 집계 필드 변경은 하나의 트랜잭션으로 처리한다.
노출 시각은 실제 대상 잠금을 얻은 뒤의 서버 UTC 시각이다. 클라이언트 시각은 받지 않으므로
지연 전송은 서버에서 처리한 시간대에 포함된다. 같은 사용자·UUID·항목의 재시도는 최초 응답을
반환한다. 대상 삭제 후에도 성공한 재시도는 유지하지만 새 UUID로 삭제된 대상을 기록하면 404다.

## 4. Today 선정

### Stage 1

1. 전날 한국 시간 기준 실제 추천 노출이 없었던 콘텐츠를 우선 후보로 삼는다.
2. 미열람 우선 → 마지막 열람 시각이 오래된 순 → 최근 저장 순으로 최대 5개를 선정한다.
3. 위 조건이 모두 같으면 랜덤으로 선정한다.
4. 5개보다 적으면 전날 노출된 콘텐츠에서 같은 우선순위로 부족한 수만 채운다.
5. 같은 콘텐츠를 중복해 채우지 않는다.

Stage 2의 최근 24시간 열람·48시간 저장 제외 조건을 Stage 1에 추가하지 않는다.
카테고리 상한도 Stage 1에는 적용하지 않으며, 항목 점수는 NULL로 저장한다.

### Stage 2 점수

`Today Score = A × 0.20 + L × 0.30 + V × 0.15 + R × 0.25 + F × 0.10`

| 요소 | 계산 |
| --- | --- |
| 저장 경과 A | `min(저장 후 경과 일수 / 30, 1)` |
| 마지막 열람 경과 L | 미열람이면 1, 아니면 `min(마지막 열람 후 경과 일수 / 7, 1)` |
| 낮은 열람 횟수 V | 0회: 1.00, 1회: 0.75, 2회: 0.50, 3회: 0.25, 4회 이상: 0.10 |
| 최근 미추천 R | 노출 이력이 없으면 1, 아니면 `min(마지막 콘텐츠 추천 노출 후 경과 일수 / 14, 1)` |
| 즐겨찾기 F | 즐겨찾기면 1, 아니면 0 |

### Stage 2 후보와 추첨

1. 현재 사용자 정상 콘텐츠에서 최근 열람 24시간·저장 48시간·추천 노출 72시간 조건으로 제외한다.
2. 후보가 5개 미만이면 추천 노출 72시간 제한을 해제한다.
3. 그래도 5개 미만이면 저장 48시간 제한도 해제한다. 열람 24시간 제한은 유지한다.
4. 남은 후보에 대해 점수를 계산한다.
5. 후보 수를 N이라 할 때 상위 후보군 크기는 `min(N, 30, max(10, ceil(N × 0.30)))`이다.
6. 해당 후보군 안에서 점수를 가중치로 사용해 중복 없이 최대 5개를 추첨한다.
7. 동일 카테고리는 최대 2개를 우선 적용한다. 복수 분류 콘텐츠는 각 소속 카테고리에 반영한다.
8. 카테고리 제한 때문에 부족하면 같은 후보군 안에서 카테고리 제한을 풀고 남은 수를 채운다.
9. 실제 후보가 부족하면 0~4개만 제공한다.

필터·점수·추첨은 배치 생성 시점에만 적용한다. 상위 5개를 점수순으로 고정 선택하지 않는다.
후보군 경계의 같은 점수는 무작위로 정하되 후보군 크기를 늘리지 않는다. 추첨 순서를 그대로
`rank`로 저장하며 점수순 재정렬하지 않는다. 카테고리 상한에는 실제 미분류 ID도 포함하고,
소속 카테고리가 없는 콘텐츠에는 상한이 없다. 음수 경과 시간은 0으로 제한한다.
기간·가중치·후보 비율·개수·카테고리 상한은 한 추천 설정 파일에서 관리한다.

## 5. Today 결과의 하루 유지

| 상황 | 처리 |
| --- | --- |
| 현재 정상 콘텐츠 5개 미만 | 항목 목록을 비우고 신규 배치를 만들지 않는다. 기존 당일 배치 정보는 유지한다. |
| 당일 배치 없음, 후보 0개 | 배치를 저장하지 않는다. 다음 요청에서 다시 평가한다. |
| 당일 배치 없음, 1개 이상 선정 | 선정 ID·순서·점수·생성 시각·기준 날짜를 저장한다. |
| 당일 배치 있음 | 해당 ID와 순서를 재사용하며 새로 추첨하지 않는다. |
| 선정 콘텐츠 삭제·열람 불가 | 해당 항목만 제외하며 보충하지 않는다. |
| 선정 콘텐츠 열람·즐겨찾기·분류 변경 | 선정 결과는 유지하고 카드 정보는 최신값을 반환한다. |
| Stage 1과 2 사이 변경 | 당일 기존 결과를 유지하고 다음 날짜에 새 Stage로 생성한다. |
| 5개 미만으로 감소 후 같은 날 다시 5개 이상 | 기존 당일 배치가 있으면 재사용한다. 없으면 생성한다. |
| 기존 배치 항목이 모두 삭제되어 0개 | 배치 생성 사실은 유지한다. 당일 재생성·보충하지 않는다. |
| 날짜 변경 | 해당 날짜 첫 유효 선정 결과를 새 배치로 저장한다. |

미생성 상태의 후보 0개와, 이미 생성한 배치의 삭제 후 0개를 구별한다.
재조회 때 최근 열람 필터를 다시 적용해 방금 본 카드를 제거하지 않는다.
사용자·Today·기준 날짜의 유일성과 트랜잭션 처리를 통해 동시 요청에서도 배치를 하나만 생성한다.
선정·배치 저장 자체는 추천 노출 카운터를 변경하지 않는다.

사용자 행은 기존 FK 삽입과 호환되는 `FOR NO KEY UPDATE`로 직렬화한다. 신규 선정 때만
본인 콘텐츠를 ID 오름차순 `FOR SHARE`로 잠그고 그 결과로 Stage와 분류를 결정한다.
잠금 이후 시각을 날짜·점수·생성 시각에 함께 사용하며, 자정이 지났으면 새 날짜 배치를 다시 확인한다.
기존 배치 경로는 전체 콘텐츠 잠금 없이 현재 개수와 선택된 카드만 조회한다.
선정 도중 추가된 콘텐츠는 다음 요청의 현재 개수에 반영하며 이미 확정된 결과는 바꾸지 않는다.
빈 결과와 기존 결과 반환도 트랜잭션을 종료하고 생성 실패 시 배치·항목을 함께 롤백한다.

## 6. Weekly Pick

### 집계와 대상

- 홈 진입 때 최신 행동을 반영한다. Today처럼 당일 결과를 고정하지 않는다.
- 저장 순위는 기간 내 유효한 저장 이벤트 행 수를 당시 카테고리별로 집계한다.
- 열람 순위는 기간 내 열람 이벤트의 당시 카테고리별 `COUNT(DISTINCT content_id)`를 사용한다.
- 같은 콘텐츠가 여러 카테고리에 속하면 각 카테고리에 반영한다. 카테고리 합계가 전체 고유 콘텐츠 수와 다를 수 있다.
- 현재 삭제된 콘텐츠의 행동은 Weekly 집계에서 제외한다.
- 미분류, 삭제된 카테고리, 현재 열람 가능한 콘텐츠가 없는 카테고리는 카드 후보에서 제외한다.
- 현재 카테고리로 과거 행동을 다시 분류하지 않는다.
- 저장 당시 미분류였다가 나중에 자동 분류된 콘텐츠의 해당 저장 행동은 Weekly 카테고리 집계에서 빠질 수 있다.
- 기간은 KST 오늘을 포함한 7개 날짜의 첫날 자정부터 잠금 이후 현재 시각까지의 `[start, end)`다.
- 이벤트 사용자와 현재 콘텐츠 소유자가 모두 일치해야 한다. 과거 NULL·빈 배열은 집계하지 않고 현재 분류·단일 `category_id`로 보충하지 않는다. 배열의 같은 카테고리 ID는 한 이벤트에서 한 번만 센다.

저장 순위 동점은 최근 저장 시각 → 현재 보유 콘텐츠 수 → 랜덤으로 처리한다.
열람 순위 동점은 최근 열람 시각 → 현재 보유 콘텐츠 수 → 랜덤으로 처리한다.
최근 행동 시각은 해당 기간 이벤트의 `MAX(created_at)`이다. 반복 열람은 고유 수를 늘리지
않아도 최근 시각에는 반영한다. 저장 이벤트를 추측해 합치지 않는다.

### 카드 선정

1. 실제 저장 활동이 있으면 `MOST_SAVED`를 먼저 선정한다.
2. 실제 열람 순위에서 이미 선정한 카테고리를 제외하고 `MOST_VIEWED`를 선정한다.
3. 행동이 없거나 중복을 피할 다른 열람 카테고리가 없으면 남은 카테고리에서 `REDISCOVERY`로 대체한다.
4. 대체 카드를 먼저 뽑아 실제 행동 카드의 카테고리를 차지하지 않도록 실제 행동 카드를 우선 확보한다.
5. 재발견은 같은 Weekly 7일 기간에 카테고리 카드 노출이 없었던 후보를 우선해 랜덤 선정한다.
6. 그런 후보가 없으면 카테고리별 마지막 노출 `MAX(recommended_at)`이 가장 오래된 카테고리를 선정한다. 동일 조건이면 랜덤 처리한다.
7. 최종 카테고리는 중복되지 않는다. 유효 카테고리가 하나면 카드 하나, 없으면 빈 목록을 반환한다.

실제 행동이 없는 카드를 `MOST_SAVED`나 `MOST_VIEWED`로 표시하지 않는다.
재발견 문구는 “다시 꺼내볼 콘텐츠가 있어요”처럼 오래 보지 않았다는 추정을 포함하지 않는 문구를 사용한다.
반환 순서는 `MOST_SAVED` → `MOST_VIEWED` → `REDISCOVERY`다. 저장 없이 열람만 있으면
열람 카드가 첫 번째다. 재발견의 기간 내 미노출 후보는 과거 노출 유무를 구별하지 않고
균등 랜덤으로 선택한다. 노출 집계는 본인 Weekly 배치의 실제 카테고리 카드 노출만 사용한다.

### 조회·배치·동시성

각 Weekly GET은 현재 행동을 다시 집계한다. 결과가 있으면 날짜가 NULL인 새 Weekly 배치와
CATEGORY 항목을 저장하고, 빈 결과는 배치를 만들지 않는다. 이전 배치·항목은 보존하며
이미 반환한 항목은 기존 노출·열람 유입 API의 규칙으로 계속 사용할 수 있다.

사용자 `FOR NO KEY UPDATE` → 현재 콘텐츠 ID 오름차순 `FOR SHARE` → UTC 시각 확정
순서로 처리한다. 이후 현재 보유 수와 행동 집계는 모두 잠근 ID 집합으로 제한한다.
도중에 커밋된 새 저장은 다음 요청부터 반영한다. 잠금과 집계를 한 SQL로 합치지 않아
잠금 대기 중 완료된 행동을 이후 집계에서 읽는다. 행동·현재 관계·노출은 각각 집계해 결합한다.
빈 응답도 커밋하고 실패하면 새 배치·항목을 전부 롤백한다. 조회 자체는 노출이나 열람이 아니다.

## 7. 삭제·기존 데이터 처리

- 영구 삭제와 마이페이지 이벤트 기반 누적 통계는 유지한다.
- 콘텐츠별 `open_count` 합계로 마이페이지 누적 열람수를 대체하지 않는다.
- 현재 남아 있는 콘텐츠의 `open_count`는 기존 `CONTENT_REOPENED` 이벤트 수로 초기화한다.
- 과거 재시도는 식별할 수 없으므로 기존 이벤트를 추측해 중복 제거하지 않는다.
- 과거 카테고리는 알 수 없는 값으로 남긴다. 현재 분류를 복사해 과거 스냅샷으로 만들지 않는다.
- Weekly의 카테고리별 집계는 스냅샷을 수집한 이벤트부터 사용한다. 초기 부족분은 재발견 카드로 처리한다.
- 추천 노출 관련 집계는 이력 없음과 0회에서 시작한다.
- 삭제 후 이벤트 보존과 추천 배치·노출의 참조 처리로 기존 삭제 API가 실패하지 않도록 마이그레이션에서 정의한다.

## 8. 데이터·코드 구성

### 데이터 구조

| 대상 | 추가·확장 내용 | 유지할 조건 |
| --- | --- | --- |
| `contents` | `open_count`, `last_recommended_at`, `recommendation_count`, `last_recommended_surface` | 기존 `saved_at`, `last_viewed_at`, `is_favorite` 재사용 |
| `content_events` | `client_event_id` UUID, `category_ids_at_event` INTEGER[], `recommendation_item_id` | 모두 NULL 허용, 행동당 본 이벤트 1행, 기존 단일 `category_id` 문맥과 누적 집계 보존 |
| `recommendation_batches` | 사용자, 유형, 기준 날짜, 생성 시각 | Today 날짜 필수·사용자별 유일, Weekly 날짜 NULL·반복 생성 허용 |
| `recommendation_batch_items` | 배치, 대상 종류·원래 ID, 실제 대상 FK, 순서, 점수·카드 유형 | 대상 삭제 시 FK만 NULL, 항목·원래 ID·순서 보존 |
| `recommendation_exposures` | 사용자, 이벤트 ID, 추천 항목 ID, 노출 시각 | 대상·위치·순위·점수는 항목→배치로 조회, 같은 이벤트 재전송 중복 방지 |

복수 카테고리 스냅샷은 PostgreSQL 정수 배열로 저장한다. NULL은 과거 분류 미확인,
빈 배열은 수집 당시 카테고리가 없었음을 의미한다. 배열 내 ID에는 현재 카테고리 FK를 걸지 않는다.
기존 `metadata_json`은 길이 제한·문자열 축약 처리가 있으므로 집계 원본을 그 문자열에만 의존하지 않는다.
이벤트·노출 ID는 각 테이블의 `(user_id, client_event_id)`로 유일하게 관리한다.
기존 이벤트의 NULL ID는 여러 건 허용한다. 배치→항목, 항목→노출·열람 유입 참조는 RESTRICT다.
카운터 음수, 잘못된 대상·점수·카드 유형, 배치 내 중복 대상·순서는 DB 제약으로 차단한다.
사용자·기간·대상별 조회 인덱스를 추가했다. Weekly의 실제 집계 쿼리 구현·검증은 5단계에서 완료했다.

Weekly의 반환 결과도 노출·열람과 연결하고 서버에서 검증할 수 있는 식별정보가 필요하다.
기존 추천 배치·항목 구조를 공유하더라도 Today의 날짜별 고정·유일성 규칙을 Weekly에 적용하지 않는다.


파일 구성은 다음과 같다. 추천 모델은 1단계, 추천 항목의 소유권 조회는 2단계,
Today 선정·배치 저장·조회 API는 3단계, 노출 수집은 4단계, Weekly 집계·선정·조회는 5단계에 추가했다.

| 파일 | 역할 |
| --- | --- |
| `backend/app/core/recommendation_config.py` | 추천 가중치·기간·개수·시간대 상수 |
| `backend/app/models/recommendation.py` | 추천 배치·항목·노출 모델 |
| `backend/app/repositories/recommendation_repository.py` | 항목 소유권·Today 배치·전날 콘텐츠 노출 조회·UUID별 노출 삽입/조회, Weekly 보유·행동·노출 집계와 배치 저장 |
| `backend/app/services/recommendation_selection.py` | 시각·난수를 주입하는 순수 Today 선정·점수 계산, Weekly 카드 선정 |
| `backend/app/services/recommendation_service.py` | Today 당일 유지·최신 카드 조회, 노출 중복 방지·원자적 집계, Weekly 기간·잠금·매 요청 배치 생성 |
| `backend/app/schemas/recommendation.py` | Today·Weekly 후보·선정 결과·응답, 노출 요청·응답 |
| `backend/app/api/v1/endpoints/recommendations.py` | Today·Weekly 조회, 노출 POST API |

## 10. 구현 단계와 완료 기준

기능·계약이 달라지면 이 문서의 현재 범위를 갱신하고, 실행한 검사와 한계는 작업별 이력에 기록한다. 과거 검사를 현재 실행 결과로 재사용하지 않는다.

| 단계 | 작업 | 검증 기준 | 상태 |
| --- | --- | --- | --- |
| 1 | DB·마이그레이션·집계 초기화 | 빈 DB 및 기존 데이터 적용, 기존 열람 수 초기화, 미확인 과거 분류 유지, 제약·삭제 호환 | 구현 — 당시 실행 결과는 작업 이력 참조 |
| 2 | 저장·열람 이벤트 수집 확장 | 모든 저장 경로의 실제 복수 분류, 반복 진입과 재시도 구분, 롤백·누적 통계 유지 | 구현 — 당시 실행 결과는 작업 이력 참조 |
| 3 | Today 선정·일별 배치·조회 API | Stage 경계, 점수·필터·추첨, 일별 유지·삭제·복귀, 동시 배치 생성 | 구현 — 당시 실행 결과는 작업 이력 참조 |
| 4 | 콘텐츠·카테고리 노출 기록 API | 실제 노출만 집계, 재시도·동시 요청 중복 방지, 열람과 분리, 사용자 격리 | 구현 — 당시 실행 결과는 작업 이력 참조 |
| 5 | Weekly 집계·카드·조회 API | 7일 경계, 고유 열람·분류 이동·삭제, 동점·중복·재발견·빈 결과 | 구현 — 당시 실행 결과는 작업 이력 참조 |
| 6 | 프론트 연동 | 실제 표시·진입, 재렌더·재시도, 카드 유형, 당일 삭제·갱신 동작 | 승인 범위 연결 — Today 상세 탐색·Weekly 카드/카테고리 이동·실제 노출·추천 유입. 운영 품질은 별도 |
| 7 | 통합 검증·문서·배포 확인 | 전체 회귀, DB migration·CI, 배포 후 저장·노출·열람 흐름을 각각 확인 | 운영 통합·공급자·실기기 확인 필요. 이번 정리에서 재검증하지 않음 |

테스트는 기존 service/API/repository/integration 구조를 따른다.

- Stage: 정상 콘텐츠 4·5·9·10개, 복수 카테고리로 개수가 중복되지 않는지.
- Stage 1: 5개 전부 전날 노출된 경우 재허용, 새 후보를 먼저 채우는지.
- Stage 2: 각 점수 경계, 24·48·72시간, 제한 완화 순서, 후보 수 올림·상하한, 중복 없는 추첨.
- 랜덤: 시각·난수 입력을 통제하여 테스트가 실행마다 흔들리지 않게 검증.
- 일별 결과: 자정 전후, 최초 후보 0개 재평가, 일부·전체 삭제 후 미보충, Stage 감소·복귀.
- 동시성: 실제 PostgreSQL의 서로 다른 연결에서 배치 중복 생성, 이벤트 재시도, 집계 증가를 확인.
- 원자성: 이벤트·스냅샷·카운터 중 하나가 실패하면 전체 롤백.
- Weekly: 같은 콘텐츠 반복 열람, 복수 분류, 분류 이동, 삭제, 미분류 자동 분류, 최근 활동 없음.
- 누적 통계: 삭제 후에도 마이페이지 횟수 유지, 카테고리 수만큼 이벤트가 증가하지 않는지.
- 접근 제어: 타 사용자 콘텐츠·카테고리·배치·이벤트 접근 차단.
- 프론트: 화면 재렌더는 추가 노출·열람이 아니며 새로운 방문·진입은 새 이벤트인지.

구현 단계에서 관련 테스트와 Ruff를 실행하고, DB 변경은 지정된 테스트 PostgreSQL에서
마이그레이션 및 모델 일치를 검증한다. 로컬 테스트, 원격 CI, 배포, 실기기 결과는 별도로 기록한다.
