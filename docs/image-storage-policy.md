# 이미지 보관 정책

2026-10-23 설계 인터뷰에서 합의한 정책이다. 코드·검증의 현재 상태는 아래에서 확인하며,
운영 전환은 별도의 실행 범위로 다룬다.
원본 보존과 계정 기반 복구의 이유는 [ADR 0001](adr/0001-preserve-account-image-originals.md),
용어는 [용어집](../GLOSSARY.md)을 따른다.

## 합의한 범위

| 항목 | 정책 |
| --- | --- |
| 보관본 | 사용자가 제공한 원본 이미지를 변환 없이 보존 |
| 기기 변경 | 같은 로그인 계정으로 재설치·기기 변경 후 다시 열람 |
| 원본 저장소 | 비공개 Railway Storage Bucket |
| 이미지 비용 목표 | 보관·전송·백업 합계 월 1만 원 안팎. 서버·DB·AI 비용은 별도 |
| 계정별 보관 한도 | 로그인 계정 300MiB, 게스트 30MiB. 모두 클라우드에 원본 보관 |
| 게스트 계정 연결 | 같은 계정을 소셜 계정으로 연결하면 기존 저장량을 유지하고 한도만 300MiB로 확대 |
| 게스트 복구 한계 | 세션을 잃은 게스트의 재설치·기기 변경 후 복구는 보장하지 않음. 이미 다른 계정에 연결된 소셜 계정과의 자동 병합은 제공하지 않음 |
| 한도 초과 | 새 이미지 저장만 제한하고 기존 이미지 열람·삭제는 유지 |
| 장기 보관 | 오래됐다는 이유로 원본을 자동 삭제하지 않음 |
| 백업 | 일 1회, 최근 7일 복구 지점. 이미지 실제 파일과 DB를 함께 복구 |
| 백업 위치 | 원본과 별도의 비공개 Railway Bucket. 일반 API 서버에는 백업 삭제 권한을 제공하지 않음 |
| 백업 효율 | 변경 없는 이미지 전체를 매일 중복 복사하지 않음 |
| 백업 손실 허용 목표 | 정상 완료된 최신 백업 이후 최대 하루치 변경. 작업 실패가 지속되면 이 목표를 충족하지 못함 |
| 사용자 삭제 | 즉시 접근 차단·계정 보관 한도 반환. 백업 사본은 최대 7일 보존 후 제거 |
| 삭제 후 복구 | 삭제 기록을 반영해 백업 복원으로 삭제한 이미지가 다시 노출되지 않도록 함 |
| 기기 캐시 | 온라인으로 권한·삭제 여부를 확인한 뒤 캐시 재사용. 완전한 오프라인 열람은 포함하지 않음 |
| 비용 목표 초과 대응 | 전체 사용량을 확인해 운영자가 신규 이미지 저장을 일시 중단할 수 있게 함. 기존 열람은 유지하고 비용 추정치만으로 자동 차단하지 않음 |

같은 Railway 안에 분리한 백업은 계정 전체 손실이나 공급자 전체 장애까지 격리하지 않는다.
백업의 7일 보존과 복원 후 삭제 상태 유지는 목표 계약이며, 삭제 기록을 보존하는 경로까지
검증해야 완료로 판단한다.

## 기기 보관 대안

게스트 원본을 기기에만 보관한 뒤 계정 연결 때 업로드하는 방식을 검토했다.
이는 로컬 원본 보관, 네이티브 공유 파일 인계, 기존 콘텐츠에 원본만 추가하는 API,
로그인 후 재개 가능한 동기화를 추가로 요구한다. 첫 구현은 모든 원본을 클라우드에 보관하고
기기의 사본은 캐시로만 사용한다. 원본의 기기 전용 보관이나 별도 동기화 기능은 추가하지 않는다.

## 구현 범위

아래 범위의 구현 명세는 [GitHub 이슈 #64](https://github.com/clip-back/clipback/issues/64)에서 관리한다.
코드 구현·로컬 검증과 운영 전환은 구분한다.

| 단계 | 변경 대상과 동작 | 확인 방법 |
| --- | --- | --- |
| 1. 저장소와 메타데이터 | `StorageClient`에 맞는 S3 구현을 추가하고 `ContentAsset`에 저장소 구분·크기·SHA-256을 기록. 기존 로컬 파일도 계속 읽기 | 원본 바이트 동일성, 로컬·S3 읽기, 저장 실패·DB 실패 정리, migration 검사 |
| 2. 계정 한도 | 서버 `user.id` 기준으로 일반 앱·공유 확장의 저장량을 합산. 알려진 한도 초과는 OCR 전에 거절하고 동시 업로드에서도 한도 유지 | 게스트·로그인 한도 경계, 동시 요청, 공유 재전송의 중복 집계 방지, 계정 승격·삭제 후 용량 반환 |
| 3. 직접 다운로드와 캐시 | 소유권 확인 API가 짧은 서명 URL을 발급. 기존 이미지 GET 유지. 새 앱은 권한 확인 후 계정별 캐시를 사용 | 타인 접근 차단, 서명 만료 재시도, Bucket에 로그인 토큰 미전송, 캐시 적중·손상·정리·계정 변경 중 늦은 응답 |
| 4. 삭제와 복구 | 재시도 가능한 파일 삭제, 복원 시에도 적용할 삭제 기록, 별도 Bucket에 원본과 DB의 일일 백업·7일 보존 | 삭제 실패 재시도, 삭제 후 오래된 백업 복원 시 재노출 방지, 사본 정리, 격리 복원 및 원본 해시 일치 |
| 5. 운영 전환 | 이미지 사용량 집계, 운영자의 신규 저장 중단 설정, 사전 검사·재개 가능한 기존 파일 이관 | 중단 상태에서 기존 조회·삭제·완료된 요청 재전송 유지, 복사 해시 확인 후 위치 전환, 중단·재개·구버전 앱 호환 |

### 구현 기본값과 기존 기능 유지

- 이미지 한 장은 현재의 10MiB 제한과 PNG/JPEG/WebP 검증을 유지한다.
- 원본 업로드와 OCR은 기존 서버 경로를 사용한다. 신규 썸네일·손실 압축·CDN·직접 Bucket 업로드는 포함하지 않는다.
- 서명 URL은 120초, 기기 캐시는 최대 100MiB·7일 미사용 정리가 초기 구현 기본값이다.
  이는 제품 보관 한도와 다르며, 캐시 정리로 클라우드 원본을 삭제하지 않는다.
- 기존 데이터가 한도를 초과해도 자동 삭제하지 않고 신규 저장만 제한한다.
  기존 파일 크기는 실제 파일에서 확인해 채우며, 미확인 자산의 크기를 0으로 취급하지 않는다.
- 계정 한도 초과와 단일 파일 크기 초과를 서로 다른 오류로 구분한다.
  본앱과 iOS·Android 공유 확장의 기존 오류 표시 영역을 사용한다.
  새로운 사용량 화면·결제 화면·로그인 유도 화면은 만들지 않는다.
- 백업 작업과 API 서비스의 권한을 분리하고, 삭제 기록이 백업 시점 이후에도 보존되는 경로를 검증한다.
  일일 백업만으로 최신 삭제 기록까지 보존됐다고 간주하지 않는다.
- 이미지 비용 집계는 보관량·백업량·신규 전송량을 구분한다. 실제 청구액을 실시간으로 보장하는 기능은 아니다.

### 완료 조건과 실행 경계

- 관련 검사와 백엔드·Flutter 전체 검사를 실행하고 결과를 기록한다.
- 프론트 변경은 iOS Simulator와 Android Emulator에서 원본 조회, 재진입, 로그아웃·계정 변경,
  한도 초과, 공유 저장을 확인하며 화면 증거를 첨부한다. 화면이 바뀌면 변경 전·후·Figma 기준을 비교한다.
  미확정 디자인은 임의 구현하지 않고 기존 디자인 확인 필요 목록에 기록한다.
- 실제 Railway Bucket 검증과 합성 S3 환경의 검증, 운영 백업과 합성 데이터 복원을 구분한다.
- API·설정·프론트 실행·배포·복구 문서를 갱신하고 최종 diff를 검사한 뒤 작업 브랜치에 커밋한다.
- 운영 Bucket 생성, 운영 설정 변경·배포·기존 데이터 이관은 코드와 검증 결과를 검토할 수 있는 상태로
  준비한 뒤 별도 실행 범위를 확인한다. 푸시·PR·머지는 별도 요청이 있을 때 수행한다.

## 현재 상태

보관 정책과 기존 인증 API 통합 테스트 중심의 검증 경계를 합의했으며,
[GitHub 이슈 #64](https://github.com/clip-back/clipback/issues/64)에 명세를 게시하고 `ready-for-agent`로 분류했다.
제품 코드와 로컬 통합 검증을 `feature/image-storage-integration` 브랜치에 모았으며 최종 코드 리뷰를 진행한다.
양쪽 모바일 실제 API 실행과 합성 DB·원본의 격리 복원 결과는
[전체 통합 검증](history/2026-10-24-image-storage-integration.md)에서 확인한다.
실제 Railway의 Bucket·권한·백업 일정 검증과 운영 전환은 아직 실행하지 않았다. 티켓별 기록은
[통합 구현 이력](history/2026-10-23-image-storage-implementation.md)에서 확인한다.
소스 확인·명세 게시·문서 검증의 기준과 결과는 [설계 인터뷰 이력](history/2026-10-23-image-storage-design.md)에 기록한다.

## 비용 해석

300MiB는 계정 한 개의 보관 한도이며 서비스 전체 비용의 상한이 아니다.
가입자 수, 신규 업로드·삭제의 반복, 구버전 앱의 API 경유 다운로드, 백업 보존량에 따라 비용이 증가한다.
백업과 복구 지점에 보관된 사본은 실제 저장 비용에서 빠뜨리지 않는다.

2026-10-23 공식 문서 기준 Railway Volume은 GB당 월 $0.15,
Storage Bucket은 GB당 월 $0.015이며 Bucket의 API 요청과 직접 다운로드 전송료는 무료다.
API 서비스에서 Bucket으로 보내는 업로드나 사용자에게 대신 보내는 다운로드에는
서비스 전송료가 적용된다. 실제 청구액에는 플랜의 포함 사용량·환율·세금 등이 영향을 준다.
